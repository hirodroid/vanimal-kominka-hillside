# IMP-WLD-008 犬との自動動画撮影カメラ

## 依頼と目的

2026-10-03 ユーザー提供「犬との自動動画撮影カメラ 仕様案」を起票。

散歩中などにVRChat標準カメラを操作し続けなくても、犬とユーザーの様子を撮影できる「専属カメラマン」のような体験を作る。犬の近くからユーザーを撮る、犬とユーザーを同時に映す、散歩に自動追従する、手ブレの少ない映像にすることを目的とする。

本Issueは仕様案と実装・検証の課題を記録する。以下の構成・性能値・録画経路は、実装や実機での成立を確認済みという意味ではない。

## 2026-10-03 回答・追加要望 (現在の方針)

- **PC専用**。PC先行で後からMobile / Questへ展開する計画にはしない。
- **モニターは出した場所に固定**し、×で閉じるまで残す。
- 対象犬の選び方を決める前に、**どういうカメラがよいかから相談する**。犬追従とユーザー追従の両パターンを扱う。
- ユーザー追従では自分だけでなく、**同じインスタンスにいるユーザーを選べる**ようにする。
- 他のユーザーを選んだら、**その本人が許可した後に撮影できる**ようにする。選んだだけで勝手に撮影を開始しない。
- 追加回答: **ユーザー追従・犬追従の2系統に、犬目線・ドローン俯瞰・スポット定点を加える**。定点は洗浄台で洗う様子と川で遊ぶ様子を、よい構図で撮れるものを用意する。
- **許可の取り方は現行のワープ (人への合流) と同じでよい**。許可が必要なのは追従・注視する相手で、背景に映り込む人は対象外。
- さらに追加: **フリスビー追従**と、**フリスビーの落下地点付近で待ち構える定点カメラ**も欲しい。
- 追加の推奨アイデアもすべて採用希望: **おかえりカメラ・ふれあいアップ・洗浄の手元アップ・ゆっくり一周・通り過ぎる散歩カメラ・おまかせ撮影 (自動切替)**。相談用だったこれらを本Issueの要望範囲へ追加する。
- **全モードで描画Camera1台・映像用メモリ1組を使い回し、選択中の撮り方だけ動かす**。ユーザー確認「そうそう。これの想定でした」により確定方針とする。

元案の「犬基準の並走1種類でMVP確定」と「すべてローカル・同期不要」は、この追加要望に合わせて見直す。撮影方式と許可の仕様を相談してからMVPの範囲を決める。

## 構成

既存の犬目線カメラ・自動撮影・写真吸着の仕組みを流用候補とする。

`追従用Camera → リアルタイム更新するRenderTexture → 撮影用モニター → VRChat標準カメラへ吸着表示 → Stream Camera等の出力・録画環境で録画`

- ワールド側の独自Cameraの位置・向きをUdonで制御する。VRChat標準カメラ自体をUdonで移動させる構成にはしない。
- 「吸着」は既存の写真表示の仕組みを指す。モニターのTransformを物理的にカメラへ追従させる必要があるか、シェーダー上の全画面表示だけで成立するかは既存実装を確認する。
- ワールド側が提供する範囲は追従映像と表示・操作。動画ファイルの記録開始・停止・保存はVRChat側の出力機能と録画環境で行う想定。PCで実際に使える録画手段・必要な操作を確認して案内する。

## ユーザー操作

1. 手首メニューなどの「撮影カメラ」を選ぶ。
2. ユーザー付近に撮影用モニターが現れる。モニターはその場所に固定される。
3. 撮影方式と追従・注視する相手を選ぶ。相手が他のユーザーの場合は本人へ撮影許可を求め、許可を待つ。
4. 必要な許可が成立してから追従映像を表示する。許可前のプレビューでも相手の追従撮影を始めない。
5. VRChat標準カメラをモニターへ近づけ、既存の吸着機能で撮影画面いっぱいに映像を表示する。
6. 利用する録画環境で録画を開始する。

終了はモニターの「×」。閉じると追従Cameraと映像更新も停止する。既存の犬目線カメラに近いUI・操作感とする。モニターは閉じるまで出した場所に存在する (ユーザー決定)。散歩中に標準カメラと離れても表示が継続するかを検証する。

## 希望する撮影方式 (2026-10-03 追加回答反映)

「何についていくか」と「何を画面に収めるか」を分けて設計する。元の7系統に推奨の撮り方5種類を追加し、下記のおまかせ撮影もユーザー要望として範囲に含める。具体的な距離・高さ・画角・切り替え操作と実装順はこれから設計する。

| 系統 | 位置の基準 | 構図の案 |
|---|---|---|
| 犬追従 | 選んだ犬のRoot付近 | 犬を主役にした並走 |
| ユーザー追従 | 自分、または許可したインスタンス内の相手 | その人の斜め前から、人と一緒に歩く犬を映す |
| 犬目線 | 選んだ犬の近くの低い位置 | 犬のそばからユーザーを見上げる。Headへ直結せず安定化する |
| ドローン俯瞰 | 高い位置。追従基準は設計時に決める | 上空から人・犬・周囲の景色が分かる俯瞰 |
| スポット定点 | ワールド内に用意した固定の撮影位置 | 洗浄台で洗う様子、川で遊ぶ様子がそれぞれよい構図に収まる |
| フリスビー追従 | 選んだフリスビーの飛行位置 | Cameraの位置はディスクに追従しながら、追いかける犬を画面に収めて撮る。注視・フレーミングの対象は犬とし、ディスクの回転をそのままCameraへ伝えない |
| フリスビー落下地点の待機定点 | 投球に対応する落下地点付近 | ディスクを追い続けず、落下地点の近くで待ち構えて、飛来・キャッチ・落下の場面を撮る |
| おかえりカメラ | ディスクを受け取る人のそばの低い位置 | フリスビーを持って戻ってくる犬が、こちらへ駆け寄る様子を撮る |
| ふれあいアップ | 選んだ犬の顔と触れ合う手の近く | 撫でる手と犬の顔を同じ画面に入れる。おやつを食べる瞬間・洗い終わった表情にも使う |
| 洗浄の手元アップ | 洗っている犬の手元・対象部位の近く | 泡をわしゃわしゃする手元やシャワーで泡が流れるところを寄って撮る |
| ゆっくり一周 | 人と犬の周囲を回る軌道 | 座っている人と犬を景色ごと、ゆっくり回りながら撮る記念動画向けの構図 |
| 通り過ぎる散歩カメラ | 橋や木陰などの撮影地点 | 人と犬が近づき、横を通り、遠ざかるまでを待ち構えて撮る |

**おまかせ撮影 (採用希望)**: 遊びや散歩の進行に合わせて上記の撮り方を自動で切り替える。フリスビーの例は「投げる人 → ディスクに追従しながら犬を映す → キャッチを待つ定点 → 戻ってくる犬」。切替条件・各カットの長さ・撮れなかったときの継続先を設計する。個々のカメラの構図を確認してから自動切替を組み合わせる。特定の人を映すカットではその人の有効な撮影許可を確認し、未許可の相手へ自動切替しない。

ユーザー追従で人＋犬、犬追従で犬を主役にする2系統の案に対し、ユーザーから犬目線・俯瞰・定点の追加希望を受けた。前・横・後ろの構図は追従系統内の設定候補。犬基準でも特定の人を注視する場合は本人の許可を必要とする。

定点カメラは**映像を撮るCameraの固定位置**を指し、**表示用モニターを出した場所に固定する仕様**とは別。洗浄台・川遊びのどの地点を何か所用意するかは現地を見て決める。定点でも特定の人を自動注視させる機能を付ける場合は本人許可の対象とし、固定構図へ背景として映るだけなら対象外とする。

フリスビーの待機定点は、常設スポットとは別に投球ごとの落下地点付近を狙う要望。落下地点の予測・既存の飛行情報からの取得・候補地点選択などの方式は調査して決める。**位置を定めた後はそこで待ち構える**構図を基本案とし、追従カメラとは区別する。犬が着地前にキャッチした場合、予測位置が変わった場合、投球前・回収中・次の投球への切替でどう撮るかも設計する。落下位置の正確な予測やキャッチ地点との一致は現時点では保証しない。対象ディスクの選び方、複数人が同時に投げた際の対象維持も決める。

追従基準の犬・ユーザーと、画面に一緒に収める犬・ユーザーの選び方は相談して決める。自分以外を選べることは必須だが、犬の自動選択や自動フレーミングは未確定。俯瞰の追従対象・高さ、各モードの細かい構図も未確定。

## MVPの共通部分 (モード数・構図は相談後に確定)

- メニューから撮影カメラ・モニターを出す
- モニターへリアルタイム映像を表示する
- VRChat標準カメラへの吸着表示を使う
- 採用する犬追従・ユーザー追従の構図で撮影する
- インスタンス内の相手を選び、本人の許可を受けてから撮影する
- 滑らかな位置・向きの更新とRoll固定で揺れを抑える
- ×でモニターを閉じ、追従Camera・映像更新を止める
- 描画・Camera・RT・モニター・追従計算はローカルとし、撮影許可の要求・応答・取消はユーザー間で伝える

元案では並走1種類が第一候補だったが、追加回答で撮影方式が増え、推奨アイデアとおまかせ撮影も採用希望となった。上記すべてを本Issueの要望範囲とし、並走1種類だけできてもIssue全体の完了にはしない。最初に検証するモードと段階的な実装順はこれから決める。複数犬を同時に収める制御などの将来候補を無断で追加しない。

## 撮影許可

**確定要件**: インスタンス内の他のユーザーを追従・注視対象に選んだら、本人の許可後に撮影できるようにする。未回答・拒否を許可として扱わない。背景の映り込みは許可の対象外 (ユーザー回答)。

**許可の取り方は既存ワープと同じ (ユーザー決定)**。参照は [IMP-WLD-001 の人への合流](IMP-WLD-001-map-warp-and-join.md) と [地図と移動の設計 §A.4](../../plans/2026-09-27-map-and-travel.md)。インスタンス内の人を選んで申し込み、相手の目の前へ通知し、本人が返答する導線を流用する。既存の「いいよ」「いまはだめ」、時間切れ、受付ON/OFF、休止・特定の人から受けない操作、通知間隔・再申請の待ち時間を基準にする。実装の入口は `KH_TravelMailbox` / `KH_TravelNotice`。

撮影依頼と分かる表示にし、ワープの許可を撮影許可として流用しない。要求・応答と許可状態は用途を区別し、撮影を許可してもワープしない。既存の受付・通知機構をどう共用するか、継続する撮影を途中で止める操作は設計時に決める。

**相談・設計案 (細部は未決定)**:

- 自分の撮影には許可ダイアログを不要とし、他の人には「誰からの撮影依頼か」を表示する。
- 許可は「撮る人と撮られる人の組・その撮影セッション」に限定する。他の撮影者や別の相手へ流用しない。
- 撮られる側が撮影中と分かり、いつでも許可を取り消せるようにする。取消時はその相手への追従・注視・映像出力を停止する。
- ×で終了、対象変更、撮影者または相手の退出で既存の許可を失効させる。古い返答・再入室・遅れて届いた許可で再開しない。
- 犬追従・犬目線・俯瞰でも、特定の人を追従・注視対象にする場合は許可を必要とする。背景の人への一括許可申請は設けない (上記の確定範囲)。
- 撮影機能はPC専用。Quest / Mobile参加者も被写体として選べるようにするか、その場合に許可・取消UIを提供するかは別途決める。

**実装側で詰めること**: 撮影者・被写体・要求の識別、本人からの返答かの照合、同時要求・連打・通信遅延・取消と許可の順序、途中参加・退出時の扱い。画面のボタンだけで許可を判定せず、追従・出力の開始条件でも検査する。詳細設計・実装前には同期・権限のレビューを行う。

この許可が制御するのは本機能の追従・注視・映像出力。外部録画ソフトそのものの開始・停止・保存を制御する仕様にはしない。

## Cameraの追従と安定化

元の犬追従案の基本式は `TargetPosition = DogRoot + CameraOffset`、向きは `LookAt(Target)`。追加要望では、選んだ犬またはユーザーを基準に位置と注視点を計算する。ユーザーの注視点は撮影者本人に固定しない。

- 犬のHeadボーンへ直接固定せず、Rootなどを基準にする。
- Position Smooth / Rotation Smoothを用い、歩行・走行・アニメーションの上下動を抑える。
- Rollを固定し、選んだユーザーの頭部または胸付近など、採用構図に合う点を注視する。
- 距離に応じてCamera Offsetを調整する。
- 「犬そのものの視点」より「犬のそばを飛んでいるカメラマン」を目指す。

実装時にはオフセットの座標系と進行方向の取り方、曲がり角・停止・急な向き変更・ワープ時の追従、対象犬が遠ざかった/無効になった場合の扱いを決める。Root追従とユーザーLookAtだけで犬とユーザーの両方が画面内に収まるとは仮定せず、構図を確認する。壁・地形へのめり込みや遮蔽、犬の体内が映る場合も確認し、必要な最小限の対処を決める。

## ローカル処理・負荷

- **確定方針 (2026-10-03 ユーザー確認済み): この動画機能の描画Cameraは撮影者の端末内で1台、ライブ映像用RTは1組を全モードで共有する。** モードの差は位置・向き・FOV・注視点・切替条件などの設定と処理として持ち、モード数だけCameraやRTを同時稼働させない。定点には撮影位置・構図のデータを置き、定点ごとの常時描画は行わない。
- 選択中の撮り方だけ追従・構図計算を行う。おまかせ撮影も現在の1カットを描画する切替方式を基本にし、全カメラの同時プレビューや2映像を重ねる切替は前提にしない。未選択の全モードで毎フレームの探索や位置計算を走らせない。
- Camera、RenderTexture、モニター、追従処理、モード選択は撮影者ごとに独立し、映像・Camera Transformは同期しない。撮影許可の要求・応答・取消に必要な状態だけをユーザー間で伝える (元案の「同期不要」を更新)。
- 通常時・終了時は `Camera.enabled = false`。撮影中のみ有効にし、必要な頻度で描画する。
- 利用者だけが追加レンダリング負荷を負う設計とする。使わない人の端末でCameraが動かないことを確認する。共通アセットの読み込み等も含む総負荷ゼロを保証する表現にはしない。
- FPS・RenderTexture解像度は既存犬目線カメラの設定を基準に検討し、PCで実測する。
- ユーザー提示の **PC 30fps前後** は候補値で、確定値・最低保証ではない。元案のMobile / Quest 8〜15fpsはPC専用の決定により対象外。
- ×で閉じた後は追従計算・RT更新も停止し、繰り返し出し入れしてもCamera・RT・モニターが増殖しないようにする。

**モード追加の費用と撮影中の費用は分ける**:

- ダウンロード容量: 既存素材を使い、設定・コード・UI中心で増やすなら、各モード追加による増加は小さく抑えられる見込み。ただしゼロや無制限を保証せず、新規画像・音源・フォント等を追加した場合は別途計測する。
- メモリ: RT共用でモード数に比例する映像バッファの増加を避ける。RT自体の確保は必要で、解像度・色/深度形式などで量が変わる。描画停止とメモリ解放は分けて確認する。
- 撮影中の描画負荷: 別視点でワールド・犬・アバターを追加描画するため、Cameraが1台でも軽いとは限らない。画角・俯瞰で見える範囲・解像度・描画頻度・影・アバターによって変わる。外部の録画処理も同じPCの負荷になる。
- 追従・自動切替の処理: 落下地点の予測、対象探索、遮蔽確認などは別のCPU負荷。モード数と同時描画数を分けるだけで、すべての処理が無料になるわけではない。

以上は設計上の見込みで、本機能の実測値ではない。ビルド容量・RTメモリ・撮影OFF/ON時のPCVR負荷を別々に測る。参考: [Unity 2022.3 Render Texture](https://docs.unity3d.com/2022.3/Documentation/Manual/class-RenderTexture.html) (実行時生成・更新と解像度/形式の設定)、[描画性能の最適化](https://docs.unity3d.com/2022.3/Documentation/Manual/OptimizingGraphicsPerformance.html)。

## 音声

音声はVRChat標準カメラの出力・録画ソフト側で取得する想定。独自Cameraの位置から聞こえる音をワールド側で再現する必要は基本的にない。

ユーザー本人が聞いているワールド音・犬の音・環境音・Voiceが、利用する録画構成でどう記録されるかを実機で確認する。映像が出ることを音声収録の成立と同一視しない。

## 構図の追加候補・将来拡張
