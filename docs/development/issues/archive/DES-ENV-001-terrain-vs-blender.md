# DES-ENV-001 地形を Unity Terrain で作るか Blender で作るか

**2026-09-22 決定: Unity Terrain を採用** (ユーザー判断「もうテレインで OK」)。以下の比較軸・切替条件は判断の経緯として残す。
舞台の骨格を決める最初の判断なので、試作 (VER-ENV-001) で確かめてから決めた。

## 判断軸 (検証前の仮説。試作の実測で確かめる)

下表は比較の観点と**仮説**であり、根拠のある実測値ではない。採否は VER-ENV-001 の条件付き実測 (端末・設定・数値) で決める。

| 軸 | Unity Terrain (仮説) | Blender メッシュ (仮説) |
|---|---|---|
| 制作速度 (地形の起伏・道・調整) | Editor 上でブラシ。試行が速い | 形状の自由度は高いが往復 (書き出し → 取り込み) が要る |
| スマホ負荷 | Detail / Tree / Layer 数で変わる。古民家の庭 (Terrain) の Android 計測 (KominkaDogRun IMP-INF-022) が参考値。`vrc-performance` で実測し「Terrain だから軽い」とも「重い」とも決めつけない (不変条件 5) | ポリゴン数とテクスチャを自分で管理できる。LOD も明示的 |
| 端の処理 (切断面を見せない) | 矩形の境界が出る。景観用の余白がどれだけ要るかは試作で見る | 端を意図した形に閉じられる |
| 草 (Paint Details) | 古民家と同じ方法が使える (秋色の草テクスチャも流用可) | 別途ばら撒きが要る |
| 道の表現 | Layer のペイント | UV / 頂点カラー / 別メッシュ |
| 古民家との連続性 | 古民家の庭は Terrain。同じ作りで質感を揃えやすい | 質感合わせを別途 |
| ベイク | 面積が大きいと Lightmap 解像度と容量の兼ね合いが要る (古民家の庭で実績あり: IMP-ENV-017) | メッシュは通常どおり |
| Udon からの操作 | Terrain は Udon から触れない (古民家 DES-PRG-002 の実測。現時点で必要な機能は無い) | Renderer なので触れる (夜演出などをするなら) |

## 2026-09-19 ユーザー判断: まず Terrain。問題なければそのまま Terrain

「比較条件は一回作ってみないと決められない」ため、Terrain で作り、微妙 / 重いとなったら Blender に切り替える。最初から Blender にはしない。

根拠 (古民家 IMP-INF-022 の実測):
- 庭 (Terrain、草 80m) の切り分けで **Terrain 草を切っても 0.1〜0.5ms**。主因は犬の Udon (約 3ms)。地面の作り方より犬・葉の透過・遠景の重なりが効き、それらは方式に依らない
- 「Blender の方が軽い」は「軽く作れば軽い」の意味。Terrain も heightmap 解像度と pixelError を絞れば小さな山は数千〜1 万三角形。差が出るのは Layer 数 (モバイルは 4 枚超で 1 パス増) と草で、設定で管理できる
- 形 (古民家が見える位置・道の長さ・端の余白) は何度も動かして決めるので、Editor のブラシで回る方が速い。固まってから重ければ heightmap を Blender へ持ち出してメッシュ化できる (作業は無駄にならない)
- 最初から Blender にすべきなのはオーバーハング・崖の抉れ・洞窟が要るとき、またはローポリの面を見せるスタイルのとき。イメージ図 (なだらかな丘 + 岩) はどちらでもない

切り替え基準 (具体):
- **微妙**: 岩場・道の段差が Terrain のブラシで作れない / 端を隠す余白で Terrain が肥大する
- **重い**: Android 実機で、草を切り Layer を 4 枚以下にしても地面が支配的 (犬 Udon・木を止めた比較の結果として)

Terrain で作るときの制約: Layer は 4 枚以下 / heightmap は必要最小 (129〜257) / 草の距離は最初から短め / drawInstanced は使用シェーダーの対応を確認してから。

## 進め方 (着手と確定を分ける)

**着手 (試作前)**: 上の切り替え基準で試作に入る (2026-09-19 に決定済み)。

1. **まず Terrain で試作する** (VER-ENV-001)。安く速く、古民家と同じ方法だから
2. 試作で次のどれかに当たったら Blender を検討する (切り替え基準):
   - 端の余白を広げても散歩道から切れ目が見える
   - Android 実機で Terrain の描画が目標 (§4 で決める数値) に収まらない (Detail / Layer を削っても)
   - 道・段差・崖の形が Terrain のブラシで作れない

**確定 (試作後)**: VER-ENV-001 の実測・画像を根拠に方式を決め、`game-design.md` §3 の地形方針を日付付きで更新し、この Issue に理由と証拠を残す。

**完了 (2026-09-22)**

ユーザー判断「もうテレインで OK」。**Unity Terrain を採用**し、Blender への切り替えは行わない。VER-ENV-001 とまとめての判断で、眺め・端の見え方は PCVR で良好と評価された。

- どう確かめたか: v1〜v4 の Terrain 試作を Editor で作って画像と Verify を取り (v4 は再読込 Verify **53/53**、Console Error **0**、Terrain 以外 **178,034 tris**。[計画 §12](../../../plans/2026-09-19-terrain-prototype.md))、ユーザーが 2026-09-20 以降の PCVR で門 → 登り道 → 見晴らし → 広場を歩いて評価した (「非常に面白かった」「かなり良かった」)。上の**切り替え基準 (端が見える / 道・段差がブラシで作れない / Android で地面が支配的) に当たったものは無い**。
- 想定と実際のずれ: 着手時は「VER-ENV-001 の条件付き実測 (端末・設定・数値) で採否を決める」見立てだったが、実際は**試作の作りやすさと PCVR の眺めの評価で先に決まり**、Android の実測を待たずに確定した。古民家 IMP-INF-022 の「地面の作り方より犬・葉の透過・遠景が効く」が覆らなかったため、負荷で地形方式を選ぶ場面が来なかった。
- 残り: Android / iOS 実機の負荷測定は未実施。地形方式の再検討材料ではなく、景観・足場の磨き込み ([IMP-ENV-001](../IMP-ENV-001-hillside-polish.md) の「負荷の初回測定」) の前提として引き継ぐ。Terrain を採用した後も Layer 4 枚以下 / heightmap は必要最小 / 草の距離は短め の制約は維持する。
