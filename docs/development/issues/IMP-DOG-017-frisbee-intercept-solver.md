# IMP-DOG-017 フリスビーの迎撃を「解く」方式へ見直す

## 要望

2026-09-26 ユーザー (PCVR 2026-09-25 のプレイ後): 「Lab はだいたいよかったが、Pome などほかの犬種は**すぐ下に回り込んでこっちを向き、跳ばずに取る**のがほとんどだった」。

「投げた瞬間に軌道・落下地点・各時刻の高さ・犬の位置が全部わかっている。なら、どの速さで走ればジャンプして取れるかもわかるはず。わかっているのに使えていないのか、わかっていないのかを確認したい。やり方を根本から見直したい。犬なので速いのはよいが、不自然に速いのは困るので犬種ごとに速度とジャンプの高さの上限を付ける」。

## 確認した事実 (2026-09-26)

### ログ (PCVR `output_log_2026-09-25_20-54-02.txt`、33 投)

| 犬 | 位置 | 結果 |
|----|------|------|
| Lab | 待機位置 (4〜8 m) | 3 投とも `jump/run` で空中キャッチ |
| Shiba | 待機位置 | 1 投は `jump/run`、2 投は `jump/wait` を選んだ後に `stand` へ落ちた |
| Pome / Dachs | 待機位置 (4〜9 m) | 10 投すべて `stand` で取る。うち 2 投は最初 `jump/wait` (rise 0.29 / 0.34) を選び、次の再計画で `stand` に落ちた |
| 全犬種 | 投げ手の横 (0.5〜0.8 m、よしよしの直後) | `overtake` を選び、次の再計画で `ground` へ落ちる (追いつけず着地後に拾う) |

- 到着見込みの誤差 `etaErr` は **-0.13〜-0.38 s** (見積もりより早く着いている)。見積もりが悲観的なので、実際は間に合うジャンプ候補が不合格や余裕 0.01〜0.3 s の候補として扱われ、次の再計画で落ちる。

### 跳べる時間帯の長さ (飛行式で計算)

跳べる帯は「口の高さ + 0.25 m (`PreferJumpMinRise`) 〜 口の高さ + `maxRootRise`」。ディスクがこの帯を通過する時間:

| 投げ | Pome / Corgi (0.54〜0.74 m) | Shiba (0.80〜1.13 m) | Lab / Samoyed (1.0〜1.6 m) |
|------|------|------|------|
| 5 m/s 10° | 74〜77 ms | 159 ms | 約 850 ms |
| 7 m/s 5° | 82〜86 ms | 175 ms | 約 1,200 ms |
| 7 m/s 15° | 49〜50 ms | 91 ms | 約 1,950 ms |
| 11 m/s 0° | 105〜112 ms | 257 ms | 約 800 ms |

プランナーは候補を **0.1 秒刻み**で調べる。そのため小型犬では、帯に入る候補が 0 か 1 個しかない。

### 今のロジック (`KH_FrisbeeCatch.Planner.cs`)

軌道は投げた時点で分かっていて、使ってもいる (`_PositionAt` を 0.1 秒刻みで 32 点)。ただし使い方が「解く」ではなく「**決まった近づき方ごとに合否を判定する**」になっている。

1. 各時刻について、近づき方の型ごとに順番に判定する: `overtake`(v3) → `hook` ジャンプ → `run` ジャンプ → `overtake` → `wait` ジャンプ → `stand` → `ground`。最初に合格した型を採る。
2. 型ごとに別の不合格条件がある。例: `run` は**早く着きすぎると不合格** (`RunJumpMaxLoiter` 0.25 s)、`hook` は輪が大きすぎても小さすぎても不合格、`wait` は `settleTime` 0.2 s の静止を要求する。
3. 10 Hz で再判定 (`KeepPlan`)。ジャンプ案は少し外れると捨てて再走査するが、その時点で帯を過ぎていれば `stand` しか残らない。`stand` は一度選ぶと「物理的に間に合う限り捨てない」ので残り続ける。
4. 余った時間の使い方を「走る速さを落とす」ではなく「輪を大きくする / 待つ / 別の型に回す」で処理している。そのためユーザー案の「間に合う速さを逆算して走る」になっていない。

**結論**: 情報はわかっていて使ってもいる。ただし使い方がユーザーの想定と違う。跳べる時間帯が長い Lab では型のどれかに当たるが、帯が 0.1 秒前後の小型犬と Shiba では、刻み幅・悲観的な見積もり・型ごとの不合格条件・`stand` の粘りが重なり、ほぼ立ち取りに落ちる。

## 決定 (2026-09-26 ユーザー)

1. **プランナーを作り直す。** 今の近づき方ごとの合否判定 (輪ジャンプ → 走りジャンプ → 並走 → 待ちジャンプ → 立ち取り) は残さない
2. **小型犬の「跳ぶ」の下限は体格に比例させる。ただし大げさでも跳んでほしい。** → 下限は体格比にして帯を広げ、帯の中では**高めの時刻を好む**ことで跳躍を大きく見せる。上限 (`maxRootRise`、小型犬 0.45 m = 体高の約 2.9 倍) は今のまま
3. **投げ手の横からでも追いかけて跳ぶ (B) を入れる。** 今の並走 (v3) は跳ばない取り方 (D') なので、入っていない
4. **取り方の使い分け**: 通常は A (回り込み) を基本とし、回り込む時間が無いときは B / C。v3 並走は B を最優先にし、足取りを速く・上下を大きくし、取ったあと走り抜けて戻る。通常の走り方と見分けがつくようにする

## 設計案 (実装前に Codex で独立レビュー)

### 解き方

1. **投げた瞬間に 1 回解く。** ディスクが犬種の跳べる帯に入る時刻と出る時刻を二分法で求める (0.1 秒刻みの走査はやめる)。帯の中を細かく (0.02 秒程度) 刻み、各時刻 t と各取り方 (A / B / C) について「踏み切り地点までの経路長」「使える時間 = t − 反応 − ため − 上昇」から**必要な平均速度**を出す
2. **成り立つ条件は物理だけ**: 必要な速さ ≤ その取り方の上限、加速と旋回を含めて間に合う、着地・範囲・地面・通り道の検査 (`LandingOk` / `DogMayGo` / `GroundOk` / `LaneClear` は流用) を通る。**早く着きすぎることは不合格にしない** (速さを落とす・弧を大きくするで使う)
3. **成り立つ候補から点数で 1 つ選ぶ**: 取り方の優先 (通常は A > B > C、v3 は B > A > C)、帯の中の高さ (高いほど良い = 大げさな跳躍)、速さの余裕 (上限の 8 割以下が良い)
4. **決めたら取り方は変えない。** 再計画 (10 Hz) は、残りの経路 ÷ 残り時間で走る速さを合わせることと、踏み切り点の微調整だけにする。取り方を変えるのは、必要な速さが上限の 1.05 倍を超えたときだけ。その順は、ほかの跳び方 → D → D' → E
5. 到着見積もりは、旋回を「走りながら回る」前提で見直す (ログの到着誤差: 待つ形 −0.13〜−0.38 秒、走る形 −0.18 / +0.01 秒)。解いた後は速さで合わせるので、見積もりの誤差は余裕で吸収する

### 犬種テーブル

犬種ごとに持つ (今は全犬種共通の値が多い):

- 通常の最高速・加速 (今は 9.5 m/s・14 m/s² 共通)、B 用の最高速 (並走の速い足取り)、旋回の速さ
- 跳ぶ下限: `min(0.25, 0.6 × 立ったときの口の高さ)` を初期値にする (Pome 0.09 / Corgi・Dachs 0.14 / Shiba 0.22 / Samoyed・Lab 0.25)。7 m/s・5° の投げで跳べる時間は Pome 83 → 140 ms、Corgi・Dachs 87 → 131 ms。PCVR で調整する
- 跳ぶ上限 `maxRootRise`・踏み切りの速さは今の値を使う

### 取り方ごとの動き

- **A 回り込み**: 落下点の先へ、横に膨らむ弧で回り込み、振り向いて落ち着いてから上に跳ぶ。余った時間は弧を大きくするかゆっくり歩くで使う。静止時間 `settleTime` は残す
- **B 追いつき**: ディスクの後ろから同じ向きに走り、走ったまま踏み切る。着地後は勢いのまま数 m 走り抜け、弧を描いて投げ手へ戻る (今は着地でその場に止まる)。v3 では足取りを速く・上下の動き (アニメ速度と跳躍) を大きくする
- **C 正面・横**: 今の「走って跳ぶ」を、速さで到着を合わせる形にする
- **D / D' / E** は受け皿として残す

### 残すもの・捨てるもの

- 残す: 同期と権限 (Owner の判断・VRCObjectSync)、BUG-DOG-003 の保留処理、空中の弾道と捕球窓・許容誤差、着地の検査、ログの `plan=N` の番号の意味 (ハーネスの約束)
- 捨てる: 輪の 8 通りの格子、`RunJumpMaxLoiter`、取り方ごとの `KeepPlan` 分岐、0.1 秒刻みの走査
- ログ: `mode=` に `around` / `chase` / `front` を足し、ハーネスをそれに合わせる。1 投の再現に要る項目 (手の位置・速度・犬の位置と向き・`dog=`) は 2026-09-26 に追加済み

### 決めること (残り)

- **B の最高速 (並走の速い足取り)。** P5 を小型犬で成り立たせるには 10〜11 m/s・旋回 480°/s が要る。「犬なので速いのはよいが、不自然に速いのは困る」との兼ね合いで決める。Lab は P5 の B が物理的に無理なので、D' (走りながら取る) を成功させる方を直す (ログでは D' を選んでも全投 E に落ちている)

## 実装記録 (2026-09-26)

Opus サブエージェント 2 本 (runtime / Editor+ハーネス) で並列実装、統括がコンパイル・Verify・ハーネスを回した。ハーネス 3 往復で確定。

### 実装した形

- **Solve** (投げの受理直後に 1 回): 跳べる帯 `[max(jumpFloorRise, minRootRise), maxRootRise]` の出入りを 0.05 秒の粗走査 + 二分法 (5 ms) で求め (区間は最大 2 つ。手元で帯に入る瞬間は届かないので 2 つ目も見る)、帯を 0.02 秒刻み (最大 60 点、両端 0.03 秒と rise 0.01 m を内側に寄せる) で A around / B chase / C front を評価。成立条件は物理だけ (必要速度 ≤ 上限、EtaCorrected ≤ 使える時間、DogMayGo / GroundOk / LaneClear / LandingOk)。点数 `pref×10 + 帯内の高さ×3 + 速度余裕×2` (通常 A>B>C、v3 B>A>C)。跳べなければ D stand → D' overtake → E ground
- **Keep** (10 Hz): 取り方は変えない。必要ペース > 上限 × 1.05 のときだけ捨てて、その取り方を除外して再 Solve。ただし**近い (B/C/D' は 1.2 m 以内、A/D は hold 内か 0.6 m 以内) か残り 0.15 秒以下ならペース判定をしない** (踏み切りの距離ゲートに任せる)。A は settle の残りが 0.15 秒を切ったら crouch の締切で判定する
- **ペース**: `PaceToArrive(d, T, vCap)` = Solve の ETA と同じ「加速してから巡航」モデルの逆算 (`v = a(T' − sqrt(T'² − 2d'/a))`、走行中は開始を s/a 秒前にずらす)。到着は A で 0.15 秒、B/C で 0.10 秒早めに狙う。B/C は残り 0.3 m まで 1.5 m/s を下回らない。旧「平均速度 = 距離 ÷ 時間」だと加速の遅れで自分の計画に追いつけなかった (Pome beside で実測)
- **B の着地後**: 減速せず `chaseSprintSpeed×0.6` で recover + 1.0 秒走り抜け (Return の最初の 1 秒)、flat の縁で止まるクランプは従来どおり。v3 の B は跳躍の再生を 1.15 倍
- **旋回**: `_speed < walkSpeed` のとき launchTurnDegPerSec (480)、走行中は 240
- **ログ**: `plan=` 行の末尾に `solve= pick= vReq= vCap= band= drop=` (drop は pace/area/landing/eta/late/expired/slot/gate/liftoff/miss)。takeoff / catch 行に `launchYaw=`。motion 判定は yawRateMax を walkSpeed 以上の区間だけ、speedMin を 1.5 m/s に初めて達した後だけで測る (静止からの向き直りと走り出しは「機械っぽさ」の対象外)
- **犬種値** (Build Scene が書く。Walking/3 Build と Frisbee/4 Build Scene の両方): chaseSprintSpeed Lab/Samoyed/Shiba 11.0、Corgi/Dachs/Pome 10.5 / launchTurnDegPerSec 480 / jumpFloorRise = min(0.25, 0.6 × 立位の口の高さ)。**小型犬 3 種は minRootRise (クリップ再生 1.8 倍の下限) 0.19 の方が高く、jumpFloorRise は効いていない** (Verify が INFO で出す)。それでも Pome の flat/mid/lob/far/side は全部 around で跳んだので、再生倍率の上限を上げる (0.19 → 0.10 なら 2.4 倍) は PCVR を見てから決める
- 削除した定数: HookCornerRadius / HookWaitPace / HookEtaMargin / StraightMaxOffAngle / PlanSamples / PlanStep / PreferJumpMinRise / ModeHook・Run・Straight・Wait。Hook* / RunJumpMaxLoiter / StandStraightSlack は Verify の参照を外した後も残置 (`kept for Verify` 注記)。次の整理で消してよい

### PCVR 1 回目 (2026-09-26 12:27 ログ) と手直し

ユーザー: 「かなり良くなった、かなり面白くなった。ただ全体的に足早すぎ、特に小型犬。回り込んだ後に全然跳ばない。追いかけながら跳ぶのは良くなった」。

ログで分かったこと (67 投):
- **回り込み (A) が踏み切り直前に捨てられて立ち取りになっていた**: Samoyed `around rise=0.70` → 残り 1.0〜1.7 m・5〜6 m/s で `drop=pace`。A の keep が経由点 (弧) を通る経路長で必要ペースを測るため、終盤に経路が 3〜5 m と読めて上限超え。→ 直線で間に合うなら経由点を終了して直進、2 m 以内は経由点なし
- **小型犬の跳躍が全部 0.32 m**: 帯が 0.06 秒以下だと中央 1 点だけを採っていた。→ 始点・中央・終点の 3 点を採り、点数の rise 重みを 3 → 6、速度余裕を 2 → 1 (RiseScoreWeight / SpeedScoreWeight)
- **追いつき (B) が `drop=gate` で 4 m 以上手前**: keep が踏み切り速度を `_speed` から再導出するため、立ち止まりからの初回で crouchStart が 2 m 遠のき、減速すると更に遠のく (逃げる目標)。→ 踏み切り速度は commit 値から上げる方向にしか動かさず、3 m 以内で固定
- **速さ**: 犬種別に下げた (Build Scene のテーブル。Verify はテーブル一致を検査)

| 犬種 | chaseRunSpeed (A/C) | chaseSprintSpeed (B) |
|---|---|---|
| Lab / Samoyed | 8.5 | 10.0 |
| Shiba | 8.0 | 9.5 |
| Corgi / Dachs | 7.0 | 8.5 |
| Pome | 6.5 | 8.0 |

その結果、**小型犬はよしよし直後の横からの投げ (6 m/s) に物理的に届かなくなった** (Pome beside: solve=0 → ground)。ハーネスの beside は全犬種 `jump|over|ground` (跳ぶなら chase) に緩めた。横からも跳ばせたいなら小型犬の sprint を 9 前後へ戻す (PCVR で判断)。
