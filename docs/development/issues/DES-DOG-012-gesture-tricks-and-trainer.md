# DES-DOG-012 左手ジェスチャーで芸を指示する・トレーナー特典の拡張

2026-10-11 ユーザー依頼。VR では左手ジェスチャー、デスクトップ等ではメニューから、お手などの芸をもっと指示できるようにしたい。追加アイデアとしての価値、実現性、負荷、トレーナー課金との相性を調査検討する。

**初期調査の結論: 追加候補として推奨。手の位置・動きと既存ポーズを使う小規模試作は現実的。指の形による多種類の指示は別途検証が必要。** 本票は採否・範囲を決める設計 Issue。調査結果を記録した段階で、機能の採用・初期公開への追加・課金変更は未決定。コード、シーン、商品設定は変更していない。

## 体験としての価値と推奨範囲

犬を見ながら手で合図し、犬が応える体験は [core-concept](../../core-concept.md) の「同じ6匹への愛着」「犬と無理なく遊べる」に合う。メニューを何度も開く手間が減り、散歩途中の休憩や写真のきっかけになる。一方、長い合図の暗記や厳しい成功判定を遊びの中心にはしない。

最初は **自分が「呼ぶ」で呼び終えた近くの犬1匹**をメニューで選び、短い「芸の指示」モードを有効にする案を推奨。VR は左手、Desktop・Touch は同じ面の動作ボタンを使う。VR にもボタンを残す。対象犬・受理した指示・使えない理由を簡潔に表示する。新規文言は既存の多言語方式へ載せる。

リードを付けたままの芸は価値があるが、現行の「呼ぶ」はリード中を除外しているため別段階。最初からリードの拒否を外したり、周囲の犬全員が反応する仕様にはしない。新モードを使わない既存のお手は現在どおり使える。

## 左手ジェスチャーの実現性

「ジェスチャー」が指の形を指すか、手を差し出す・下げる等の動きを指すかは未確定。方式を混同して実装可能と約束しない。

| 方式 | 判断 | 根拠・制約 |
|---|---|---|
| 左手の位置・向き・短い移動で指示 | **最初の試作に推奨** | `GetTrackingData(LeftHand)` で取得でき、既存のお手にも実績がある。犬/頭に対する相対位置で判定し、体格・座位でも届く範囲を試す。掌の向きの解釈は機器差を確認する |
| グー・パー・チョキ等の指形で指示 | **条件付き候補** | アバターの `GestureLeft` は Animator のパラメータ。ワールドUdonへその値が自動で来る前提は置けない。公式入力イベント一覧には対応する直接イベントが掲載されていない。指ボーンからの推定なら可能性はあるが、ボーン欠落・独自の手ポーズ・アバター変更・指追跡の有無で結果が変わる |
| 左手ボタンと手の動きの組み合わせ | 誤発火が多い場合の代案 | `InputUse` / `InputGrab` は左右付きで取得できる。移動・Pickup・メニュー操作との競合を確認。グリップ押下をグー等の指形と同一視しない |
| Desktop・Touch のメニュー | **必須** | 同じ対象犬・芸ID・所持判定・同期要求へ接続する。VR専用の特典にしない |

公式根拠: [Input Events](https://creators.vrchat.com/worlds/udon/input-events/)、[Player Positions](https://creators.vrchat.com/worlds/udon/players/player-positions/)、[Avatar Animator Parameters](https://creators.vrchat.com/avatars/animator-parameters/) (2026-10-11参照)。直接イベントが掲載されていないことからの方式判断であり、全てのSDK APIが不存在という証明ではない。今回の Wrapper DLL の文字列探索は既知の取得APIも抽出できず、公開可否の証拠に採用しない。

専用アバター改変・OSC・外部アプリを参加者に必須とする案は、アバターに何も付けず成立させる企画方針に合わない。指形を採るなら、標準的な複数アバターでの判別結果と、判別できない場合のボタン操作を先に確認する。

### 誤発火と競合への対策案

- 操作対象を1匹に固定し、近距離・犬の到着後・明示的なモード中だけ判定する。初回の試作値は距離2m、保持0.35〜0.5秒を起点とする (既存値からの仮案。未測定)。
- 同じ合図を保持しても1回だけ受理し、手を中立へ戻してから次を受ける。芸の再生中は新しい芸を割り込ませず、終了/取消を優先する。遅れた要求は世代番号等で捨てる。
- 左手で道具やメニューを持っている時、配置操作中、トラッキングが無効な時は開始しない。対象犬が解除・退出・リード接続等で利用不可になったら止める。
- おやつ・撫で・洗浄・ボール・フリスビー・集合・ライブと競合させない。進行中の行動を勝手に奪わず、最初の試作では競合中の開始を拒否する。
- 既存のお手/あご乗せの手判定と新しい指示判定が同時に芸を要求しないよう、モード中の担当を1つにする。

## トレーナー課金との関係

**推奨: 操作方法と芸の利用権を分け、既存の芸は現在の権利を維持、新規の芸セットを既存トレーナー特典に追加する。** 採用・商品説明の変更は未決定。

| 案 | 評価 |
|---|---|
| 既存のお手等を月額専用に変える | 非推奨。既存のポイント解放を失わせ、基本のふれあいを狭める |
| ジェスチャー操作だけトレーナー専用 | 第一案にはしない。Desktop・Touchには新しい遊びが増えず、入力の都合で価値が偏る |
| 既存の操作・権利は維持し、新しい芸をトレーナーへ追加 | **推奨**。「トレーナー」の役割に合い、全端末で同じ芸を楽しめる |
| 新しい芸もポイント解放、または別の買い切り商品 | 比較候補。入りやすさ/永続利用は利点だが、既存トレーナーを充実させる目的には直接つながらない |

推奨案では、既存芸は所持済みならジェスチャーでもメニューでも使える。追加芸はトレーナー所持者が指示でき、周囲の未加入者も犬の芸を見られる。課金は他人の利用中の犬を取り上げる権利にはしない。

実装時は既存 Product / Listing と `KH_TrainerPass` を再利用し、メニューを隠すだけでなく受信側で**送り手**の所持権・対象犬の操作権を検査する。未ロード時は許可しない。現在のパスは滞在中の失効で権利を落とさず、再入室時に判定する実装なので、その扱いも採用前に確認する。既存ポイント所持を消したり、新しい芸を永続購入済みとして保存したりしない。

公式ではサブスクリプションに Udon Product を含めてワールド機能を提供できる ([Products](https://creators.vrchat.com/economy/products/)、[Subscriptions](https://creators.vrchat.com/economy/subscriptions/)、2026-10-11参照)。この一般機構と既存コードから技術的には適合する。実際の購入・両ワールド間の認識・Store動作を今回確認したわけではない。

### 方式の提案

初期調査の「短い芸の指示モードをメニューで有効にする」案は**採らない**。既存のお手の手判定 (`UpdatePaw`) を芸の数だけ拡張すれば足り、モードの ON/OFF と対象犬の選択を増やさない。初期調査の誤発火対策のうち「中立へ戻してから次を受ける」「芸の再生中は割り込まず終了を優先」「使えない条件では判定しない」は維持し、「遅れた要求を世代番号で捨てる」は既存の `calledMs` 世代がその役を果たすので新設しない。保持型なので終了期限も置かない (手が離れれば終わる)。

**VR の入力**: 既存 `UpdatePaw` と同じ「手の位置ゾーン + 保持」。芸ごとに犬基準の目標点と半径を Setup が算出する (お手の `pawTargets` と同じ経路。配列を芸の数だけ持つ)。

| 芸 | 目標点 (犬のローカル) | 犬の動き |
|---|---|---|
| お手 (既存) | 左前足の先 (Bone.014_L)。既存の `pawTargets` | 左前足を手に乗せる (保持型) |
| おかわり | 右前足の先 (Bone.014_R)。生成したクリップから算出 | 右前足を手に乗せる (保持型) |
| ハイタッチ | 鼻先の前方で頭より高い点 (生成したクリップの前足の先から算出) | 座ったまま前足を立てて掌に当てる (保持型) |

- 判定値はお手の現行値から始める: 半径 max(0.06, r)、保持 0.35 s、手の速さ < 0.45 m/s、保持中は半径 1.4 倍、外れて 0.15 s で解除。
- **ゾーンの選び分け** (お手とおかわりは小型犬で中心の間が 10 cm 程度、半径の下限 0.08 m なので重なる): 1 匹につき候補は**最も近い目標点 1 つ**だけ。2 番目に近い目標点との距離差が半径の 0.5 倍未満 (曖昧な領域) なら受理しない。候補が変わったら保持時間を 0 に戻す。保持が成立している間は他の芸を判定しない (手が離れて解除されるまで)。ハイタッチへ上げる途中にお手のゾーンを通るときは、速さ < 0.45 m/s と 0.35 s の保持が守る。
- **使う手**: 既存のお手と同じ**犬に近い方の手** (左右どちらでも)。ただし**道具を持っている手は候補から外す** (`GetPickupInHand`。KH_HandWash と同じ型)。手元メニューは Pickup ではないので外せない (右手でメニューを操作しながら左手で芸をする想定は成り立つ)。左手固定を選ぶ場合は既存のお手もまとめて左手固定にする (芸ごとに規則を変えない)。
- 指形 (グー・パー・指差し) は**第一段では使わない**。使うなら後段で、`GetBonePosition` の指ボーン (指先と手首の距離で開閉を見る) を複数アバター・Quest の指追跡・指ボーン無しで試してから足す。判別できないときはゾーン判定に落ちる。

**Desktop・Touch・VR のボタン**: 呼ぶタブのポーズ面 (既存 `pawButton` の並び) に [おかわり] [ハイタッチ] を足す。2 m 以内、4 秒保持 (既存 `_desktopUntil` と同じ)。新しいタブは作らない (タブ構成 A は決定済み)。VR の優先規則: ボタンの保持中 (`_desktopUntil > now`) は手判定を止め、ボタンの芸を出す。期限で解除。同じボタンの再押下は解除 (既存のお手と同じ)、別の芸のボタンは置き換え。ボタンの期限が切れたら手判定に戻る。手判定が保持中はボタンを押せず点灯だけ。

**対象犬・姿勢**: 自分が呼んで到着した 1 匹 (`IsSleeperLocal`) がおすわり (PoseId 2) のとき。あご乗せ (PoseId 1) 中・伸び中・おやつ中 (`CalledTreatActive`)・配置中・`CallPending` は不可 (お手と同じ条件)。リード中の犬は呼べないので、散歩中の芸は初期範囲外。

**同期**: `pawHeld` (bool) を `pawKind` (int: 0 無し / 1 お手 / 2 おかわり / 3 ハイタッチ) に置き換える (同期変数の数は変えない)。要求は 8 引数のまま、`op` を芸ごとに分ける (`Paw` / `Paw2` / `HighFive`)、`flag` は保持。受信 (`HandleRequest`) の規則: 「要求値 = flag ? 芸 : 0」とし、`pawKind != 要求値` なら更新する (1 → 2 → 3 の切り替えを「保持は true のまま」として捨てない)。`pose == poseId` と `poseId == 2`・`!StretchActive` の条件は既存どおり。送り手側の `_pawRequested` は int (要求値) にし、再送 2 s と世代 `calledMs` はそのまま。Animator: `States` の末尾に CallPaw2 (8) / CallHighFive (9) を足し、`pawKind` 1 / 2 / 3 → CallPose 3 / 8 / 9。犬側の遷移・解除・移動復帰は CallPaw と同じ型。保持型なので途中参加は状態の同期で揃い、終了も `pawKind = 0` で全端末に届く。Owner 交代時の再要求、呼んだ本人の退出での解除は既存のまま維持。一発型の `stretchMs` 系は使わない。

**権利**: 検査の置き場所は `HandleRequest` (Owner の直接呼び出しも `RequestSlot` もここを通る)。規則: **0 は解除 (検査なし)、1 は送り手の `ActionOwnedBy(GivePaw)`、2・3 は送り手の `KH_TrainerPass._OwnedBy`、それ以外の値は拒否。** 参照が無い (TrainerPass 未配線) ときも拒否。既存の `!flag || ActionOwnedBy(...)` の形は「芸 ID と flag=false の組」が検査を通るので使わない ([BUG-DOG-009](BUG-DOG-009-frisbee-style-receiver-check.md) の型)。未ロードは拒否。滞在中の失効は再入室で判定 (現行の方針)。送り手側も同じ判定で早期に落とし、未所持の人には看板と同じ案内 ([購入画面をひらく]) を出す。

**競合**: 既存のお手の条件をそのまま使う。集合・フリスビー・リードは「呼ぶ」の入口 (`_IsWalkBusy`) で、洗浄は犬側 (`WashYieldsToErrand`) で、呼ばれている犬から外れている。

**文言** (13 言語、`KD_Language`): 新設は芸名 2 つ (ボタン) と案内 2 つ (`call.paw2Hint` / `call.highFiveHint` 相当)。使えない理由は既存の `call.lockedHint` と `call.unavailable` を流用し、トレーナー未所持だけ新しい 1 文 (購入画面への案内) を足す。

### ユーザーに決めてもらうこと (推奨つき)

1. **入力の方式** — 推奨: **手の位置ゾーン + 保持 (お手と同じ型)。** 指形は第一段で使わない。理由: 既存の実績値と Setup の経路をそのまま使え、アバターに依存しない。指形は後段の試作が成立したら足す。
2. **使う手** — 推奨: **犬に近い方の手 (左右どちらでも。道具を持つ手は除く)。** 左手固定にしない。理由: お手と同じ振る舞いで、利き手・座る向きの差を吸収する。左手固定を選ぶなら既存のお手も左手固定にする。
3. **第一段の芸** — 推奨: **おかわり と ハイタッチ の 2 種。** 理由: お手の判定・同期の経路を流用でき、クリップも Unity の Editor スクリプトで 6 犬種分が出る。おまわり・ごろんは Blender の新規モーションで別 Issue。1 種だけにする場合はおかわり (お手に最も近い)。
4. **権利** — 推奨: **第一段の芸はすべてトレーナー特典。既存の 4 動作は現行の 30pt のまま。トレーナーの価格は今回変えない** (価格の判断は [DES-UI-005](DES-UI-005-trainer-and-paid-items-purchase-flow.md) が持つ)。注意: トレーナーは古民家と同じ Listing なので、特典に芸を足すと Listing の説明と古民家側の案内も変わる。「特典の範囲」は DES-UI-005 でも決定待ちなので、両方を一度に決める。**芸が使えるのは裏山だけ** (古民家には実装しない)。**提供前に販売説明へ載せない** (初期公開の看板・Listing は現行特典のまま。芸を出した版で DES-UI-005 と古民家側の案内を更新する。古民家側は別 Issue を古民家の repo に起こす)。代案: 各 30pt のポイント解放 (入りやすいが、トレーナーの充実にはならない。この場合 Listing の更新は不要で、6 の「足並み」の理由も消える)。
5. **対象犬** — 推奨: **自分が呼んで到着した 1 匹、おすわり中。** リード中・周囲の犬全員は対象外 (初期調査どおり)。
6. **公開時期** — 推奨: **初期公開には入れず、公開後の最初の追加。** 理由: 初期公開は Play・実機の確認待ちが多く (2026-10-12 時点で review 75 件)、4 で特典にするなら Listing の変更は古民家と足並みが要る。実装 Issue だけ先に起こしておく。代案: 初期公開に入れる (実装 1 波 + 独立レビュー + Play 確認が増える)。
