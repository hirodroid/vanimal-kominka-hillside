# DES-DOG-011 シャンプー泡を立体的なもこもこにする方式と負荷の検討

親は [IMP-DOG-024](IMP-DOG-024-walk-and-wash-experience.md)。2026-10-11 のユーザー依頼に基づく調査・検討。**今回の調査は完了、方式の採用判断は未了**のため wip とする。実装・本番シーン変更・Play・端末計測は今回行っていない。

## 要望

今の洗い心地は良いが、泡を全身につけても表面がつるっと平らに見える。体の上に丸い泡が積もるもこもこ感と、シャワーで崩れて流れ落ちる感じを増やしたい。現行方式が負荷のためなのか、いったんシェーダーで進めただけなのかを調べ、負荷が増えすぎる方式は採らない。流体シミュレーションそのものが要件ではなく、簡易表現も比較する。

方針の正本は [core-concept §1・2・3](../../core-concept.md) と [game-design の散歩帰りのお手入れ](../../game-design.md)。洗う気持ちよさ、犬の顔・特徴の読みやすさ、PCVR・Quest単体・iOSの快適さを両立する。既存機能の完了判断を取り消すIssueではなく、追加の表現改善として扱う。

## 1. 調査結果：なぜ現在の方式なのか

調査対象: Unity 2022.3.22f1、HEAD `ccda9a2` 時点の作業ツリー。洗浄のシェーダー・実行コード・Setup・保存マテリアルと設計書・git履歴を照合。他作業の未コミット差分は変更しない。ユーザーが今回見た端末・ビルド版は未特定であり、下記のどの描画経路を見たかは断定しない。

| 確認事項 | 根拠と結論 |
|---|---|
| 最初の採用理由 | [方式設計 §1](../../plans/2026-09-30-dog-wash-design.md) は、購入済みの毛のマテリアルを改変せず、端末差を避けながら局所的に塗り・すすげるよう、同じ体メッシュ・骨を持つ追加SkinnedMeshRendererとUVマスクを採用している。「粒子版を計測した結果、重いので不採用」とする記録は確認できなかった |
| PCの泡 | `KH_WashShell.shader` は D3D11 用に泥・濡れ1パス＋泡4層。各層を法線方向へ押し出し、高さの模様で切り抜く。柴の保存マテリアルは `_BaseOffset=0.005 m`、`_FoamThickness=0.05 m`。単なる白い色塗りからは既に改善しているが、個々の泡を閉じた丸い立体として作ってはいない |
| PCで粒子を見送った経緯 | `908339b` で1層から多層へ変更。`a0b533c` ではPCVRの「層の切れ目」への対処を優先し、泡粒子を重ねる案を保留。[IMP-DOG-025 の2026-09-30記録](IMP-DOG-025-wash-prototype-one-dog.md) と [方式設計 §8](../../plans/2026-09-30-dog-wash-design.md) に明記。粒子比較の結果ではなく、シェーダーの切り口改善を採った段階 |
| モバイルの平面化 | `7a84a47` で、旧3パス（泥・濡れ＋泡2層）から、泥・濡れ・泡をまとめた1パスへ変更。現行の非D3D11経路は泡の厚い層を持たない。[IMP-ENV-010 §4](IMP-ENV-010-quest-performance.md) のQuest 3報告を受けた、明確な性能対策 |
| 過去の性能根拠の限界 | 同記録は、犬Udonを止めた状態で犬が見えると30〜40 fps、視界から外すと60〜70 fps、殻の再有効化によって初回のRenderer OFF比較が妨げられたと分析している。**現行版や粒子版とのA/B実測ではなく、泡だけのGPU時間でもない**。立体泡全般が不可能という証拠にはしない |

なお、旧試作書 §5 と方式設計 §3 の予算表には非PC「2層／3パス」の旧記述が残る。現行の判断はシェーダー実装、方式設計 §1-3、`7a84a47` を優先する。この調査では旧資料全体の改訂は行わない。

### 平らに見える理由（実装からの推定）

PCの4層は体と同じ形の面を一定間隔で押し出したもの。泡の山は各面上の切り抜き・陰影で表すため、丸い側面・細かい凹凸の視差には限界がある。泡が十分増えると上側の層が広く覆い、面として読まれやすい。モバイル経路では立体の層自体を削っている。今回の見た目を現行実機で再現確認した原因確定ではない。

### 粒子も、すでに一部使っている

`KH_DogWash.ContactEffects` はボトルで6粒、スポンジ・手・泡がある場所へのシャワーで `foamPuff` をEmitする。Setupの泡側設定は Billboard、World空間、上限80粒、寿命0.8〜1.4秒、サイズ0.01〜0.03 m、重力係数 −0.03。これは接触点から漂って消える補助演出であり、体を覆って残る泡ではない（数値はSetup設定。現在のEditor内実体を照合した値ではない）。

`KH_WashMask.FragRunoff` は、すすいだ近傍8方向の画素数に応じて残った泡と泥を減らす。**重力方向への移流や、泡の塊が体から離れて落ちる処理ではない。** 現在の「流れて消える」手応えを保ちつつ、流下する立体演出を別に足す余地がある。

## 2. 方式の比較

以下の負荷評価は仕組みからの予測で、同条件の実測順位ではない。粒子にもシェーダーが必要なので、比較軸は「シェーダー対パーティクル」ではなく、形・描画回数・更新処理・透過の重なりである。

| 候補 | もこもこ・流下の表現 | 主な負荷・難点 | 今回の評価 |
|---|---|---|---|
| A 現行シェルの調整・層追加 | 模様・陰影は改善できる。層を増やせば厚みの段差は減るが、粒の丸い側面や落下は別処理 | 全身メッシュをパスごとに描き、画素のノイズ計算も重なる。PC4層増量・モバイル多層への復帰は過去の負荷問題を再発させ得る | 比較基準。色や光沢だけの変更では要求を満たしにくい |
| B Billboard粒子で全身を覆う | 球状の陰影を描いた板で粒感を出せるが、近接VRでの真の形状・視差は弱い | 透過の重ね描き。アニメーションする体への付着と局所すすぎの制御も必要 | 今回の主方式には弱い。離れた飛沫の補助向き |
| C Mesh粒子で全身を覆う | 小さい丸い3Dメッシュなら実形状を持つ。落下・縮小も粒子機能で表現可能 | 粒数×頂点数、粒子更新、描画、体への追従制御。Local/Custom空間だけでは複数の関節の変形に付着し続けない | **粒子版の比較候補**。重いと断定して落とさないが、全面付着を最初から任せると実装量が大きい |
| D 付着用の泡塊メッシュ＋流れる短命Mesh粒子 | 体に残る丸い輪郭をメッシュで、剥がれ・流下を少数の粒子で作れる。薄い泡とすすぎの細い境界は既存マスクで維持 | 付着メッシュのスキニング・マスク参照と少数粒子の増分。既存4層に足すだけだと純増。泡同士の継ぎ目・関節・顔は要確認 | **第一比較候補**。現行4層を一部置換できるかも測る |
| E 球の融合を画面／レイマーチで描く、流体シミュレーション | 滑らかな融合・流れを狙える | 画素ごとの反復計算、追加描画／RT、シミュレーション、VR両眼・モバイル・Udonへの統合検証が増える | 本調査では後順位。簡易メッシュ案で満たせない時だけ再検討 |

Unityの [Renderer module](https://docs.unity3d.com/2022.3/Documentation/Manual/PartSysRendererModule.html) は、Billboardと3D Meshを区別し、Billboardの球状陰影も実体は板として説明している。 [Shape module](https://docs.unity3d.com/2022.3/Documentation/Manual/PartSysShapeModule.html) のSkinnedMeshRenderer指定は発生元、[Main module](https://docs.unity3d.com/2022.3/Documentation/Manual/PartSysMainModule.html) のLocal/CustomはTransformに対する座標空間である。これらだけで発生後の粒子が体のスキニングへ固定されるとは扱わない。

[GPU Instancing](https://docs.unity3d.com/2022.3/Documentation/Manual/PartSysInstancing.html) はMesh粒子と対応シェーダー等が条件（カスタムシェーダーは target 4.5以上）。全端末で自動的に効く、粒子シミュレーションまでGPU化される、追加SkinnedMeshRendererにも同じ効果がある、とは見積もらない。[VRChatのAndroid最適化資料](https://creators.vrchat.com/platforms/android/quest-content-optimization/) でもワールドのカスタムシェーダーは禁止されておらず、透過によるフィルレート消費が注意点。アバターの粒子数制限をワールドの上限として流用しない。（一次資料確認日: 2026-10-11）

## 3. 推奨する最小試作の設計案（未採用）

**Dを第一候補、Cを粒子版の対照、現行を基準にする。流体計算を入れなくても、丸い塊・縮み・少量の落下を組み合わせれば要求に近づけられる見込みがある。** 負荷が現状以下になるかは未確認。

### 体に残る泡

- 球を大量に撒くより、大小の丸い山がつながった低密度の泡塊を作る。ほぼ不透明・柔らかい陰影・少ない光沢を基本に、真珠やぶどうの粒、均一な白い服に見えないようにする。薄い部分の細かい泡はマスク側に分担する。
- 代表1匹の体表に、泡塊の中心・体表のUV・法線・近傍の骨ウェイトをEditorで焼く案。塊は結合した追加SkinnedMeshRendererにまとめ、個々の粒をGameObject/Udonにしない。泡塊の中心と体表UVを追加頂点属性に持ち、既存のマスクGを頂点段で読み、泡の量で中心から膨らむ／縮む案を検証する。追加属性の中心が自動的にスキニングされるとは仮定せず、中心も同じ骨変換へ追従させ、変形後の頂点と同じ座標系で伸縮する方法を最初に確認する。塊内の骨ウェイトの扱い、関節での変形と表面からの浮きは未検証。
- 粗い泡塊がすすいだ細い帯へ張り出さないよう、塊の大きさ・中心UVだけでの制御・縁のマスク切り抜きを比較する。縮めた粒にも頂点処理は残るため、泡が無い犬ではRendererを止める。
- PCは「現行4層に追加」と「泡層の一部を置換」を区別して測る。モバイルは現在の1パスを基準に、少数追加が許容できるか別判定。6匹への自動展開は採否後。

### 洗い流す泡

- マスクによる帯状のすすぎと清潔判定を維持し、当たった付近の泡塊が縮むのと合わせ、重力・速度・寿命・縮小で動く短命のMesh粒子を出す。
- 最初は「接触点付近から短く下へ動いて離れる」演出に限る。体表に沿って滑り続けること、泡同士の衝突・合体、床に溜まる泡の保存は初回に入れない。重力だけでは犬の中を通り得るため、発生位置・外向き速度・寿命を調整し、必要なら表面上の短い経路を追加する。
- 出しっぱなしにせず、泡のあるすすぎに限定し、犬ごと・全体の上限を設ける。既存 `foamPuff` は手洗い／ボトルにも共用なので、重力を一括変更せず流下用途を分ける。
- 見た目の粒を同期の正本にせず、既存の操作・セル・マスクからローカルに演出する。粒子位置の新規連続同期は不要な案とする。途中参加は残った泡を現行の復元マスクから表示し、過去の落下粒子を再生しない。既存の粗い途中参加復元より高精度になるとは約束しない。

### C（全面Mesh粒子）で先に確かめる難点

発生位置だけをSkinnedMeshRendererにしても付着は保証されない。体表の固定サンプルを骨へ追従させて粒子の位置を更新する案、骨単位のCustom空間へ分割する案を比較し、Udonからの粒子更新APIの公開とコストを試作前に確認する。RTを毎フレームCPUへ読み戻して粒を振り分ける設計を前提にしない。粒子を個別にすすぐための体表UVとマスク参照方法も必要。Dより更新負荷・作業量が少ないと確認できた場合はCを採ってよい。

## 4. 比較の規模・計測・採否

初回探索の**提案値（性能保証・確定予算ではない）**: 付着泡塊32→64→128個、1塊40〜80三角形、流下粒子は同時8→16→32個。64塊×80三角形なら追加形状は5,120三角形／犬、6匹なら30,720三角形になる計算だが、これは描画回数・頂点属性・スキニング・画素負荷を含む性能値ではない。少数で全面もこもこを満たせない場合は、ただ粒数を増やす前に塊の形と配置を直す。

| 順 | 実施内容と残す証拠 |
|---|---|
| 1 静的・Edit確認 | Udon API、メッシュ属性・骨・マスクUV、ステレオ対応、Bounds、対象端末シェーダーのビルド可否。主洗い場・柴1匹の「薄い泡／全身泡／すすいだ帯」で現行・C・Dの同条件画像。白毛・小型犬への簡易表示も早期に行う |
| 2 最小の動作比較 | 動く足・首・尾、手での泡立て、すすぎ中の追加泡、全身泡から終了、道具停止で粒子が止まり消える、歩行復帰で泡が宙に残らない。近接で上・横・斜め、昼／夜を比べる。視距離は実際の洗い位置を記録し、試作の暫定カメラ値を確定値にしない |
| 3 負荷比較 | 同じ端末・版・視点・解像度・状態で、基準→候補→基準へ戻す。1匹と6匹分の泡表示、複数地点の同時すすぎ（実際の同時数を記録）、未使用時を分ける。代表ケースを複数回、ウォームアップ後に計測 |
| 4 端末・通信 | PCVR、Quest単体、iOSを別記録。CPU/GPUフレーム時間の取得可否、中央値と悪い側の値、batches／SetPass／三角形／生存粒子、スキニングと粒子更新の増分、メモリ・容量を記録。2人で同じ犬、非Ownerの操作、途中参加・Owner交代の見た目も確認 |

初回の計測前に各端末の現行フレーム予算と余裕から許容増分を決める。**GPU／CPU時間が継続して増え、現行の快適さを崩す案は採用しない**。FPS上限に張り付いているだけで「負荷ゼロ」と判断せず、EditorのFPSをPCVRの性能へ読み替えない。端末のGPU時間を取得できない場合はその制約と代替の比較結果を明記し、推測値を埋めない。

採用候補は「立体感・流れ落ちる気持ちよさが明確に改善」「洗った帯と泡が一致」「顔と犬らしさが読める」「端末別に許容負荷内」の全条件を満たすもの。PCだけ成立する場合もモバイル合格にせず、端末別の粒数・形状・無効化を検討する。現行より良くならない／負荷が許容できなければ現行を維持する。

次の作業は上記の代表比較試作。Playはプロジェクト共通ルールに従い事前相談・専用ハーネス経由とし、全体回帰はユーザーの明示指示がある時だけ行う。今回の依頼から全面実装や長いPlayを開始していない。
