# DES-WLD-003 地図・地点ワープ・プレイヤーへの合流

2026-09-27ユーザー要望。コース拡張に伴い、地図とポイント間のワープ、フレンド/プレイヤーの近くへ合流する機能が欲しい。リードでつないだ犬も一緒に移動する。景観制作とは別Issueとして残す。

## 設計する内容

- 地図：既存の登り道・奥広場・橋2か所・川岸・入口、現在地と方向。Desktop/VR/Touchで読める大きさと操作。
- 地点ワープ：入口/既存広場/奥広場/川辺などの安全な足場。水面/橋/斜面/他人と重ならない着地点。
- 合流：在室プレイヤーをどう選ぶか、相手の受入れ/拒否、退出/移動中/水中の扱い。フレンド判定APIが利用できると仮定しない。相手を強制移動する機能ではない。
- 同行：両手のリード最大6匹を対象に、接続・左右・Owner・目的地を維持する。通常の追従がプレイヤーのTeleportだけで必ず成立するとは扱わない。犬/紐の伸び・旧地点への引戻し・非Ownerの要求を調べる。
- 誤操作対策、短時間の連打、到着後の向き、散歩を続ける場合と入口へ戻る場合の扱い。

## 受け入れ条件

- [x] 地図と地点/プレイヤー選択の画面・操作仕様を決める。
- [x] 1/3/6匹、片手/両手、他人の犬を動かさない条件を定義する。
- [x] 同期・退出・途中参加・Owner交代で二重移動/置き去りがない検証手順を持つ。
- [x] VR酔い、Touch操作、到着位置と安全な失敗時動作を確認する。

## 決定 (2026-09-27)

ユーザーが「ユーザーに決めてもらうこと」5 件に回答し、設計を確定した。回答の要旨は次のとおり (音声の書き起こし)。「地図はフレンドを取得するのではなく、インスタンスにいるプレイヤーを選択して、フレンドかどうかに関係なく合流できる。それで大丈夫。テレポートは川と奥の広場ぐらいかな。あとは推奨でやってくれているもので OK」。

1. **ワープは、川辺と奥広場の 2 か所で初期公開する。** 入口 / 既存広場 / 上流の橋の手前 / 下流の橋の手前は候補として設計書に残し、初期公開では出さない。追加は Play の後にユーザーが決める。合流は初期公開に含める。フレンド判定は使わず、インスタンス内のプレイヤーを選ぶ。
2. 地図は、推奨どおり「さんぽ」タブの副画面に置く。
3. ワープした後の行き先は、推奨どおり変えない。
4. 合流の受け付けの初期値は ON。断りと時間切れは「今は合流できないようです」と出し、対応中と休止は分けて出す (推奨どおり)。
5. 地図に出すのは、選んでいる相手だけ (推奨どおり)。

受け入れ条件 4 つは、設計書の §A〜§D (決定を反映したもの) で満たした。実装と、ClientSim・PCVR・端末での検証は [IMP-WLD-001](IMP-WLD-001-map-warp-and-join.md) で行う。

## 設計 (2026-09-27)

設計書: [地図・地点ワープ・プレイヤーへの合流の設計](../../plans/2026-09-27-map-and-travel.md)。**受け入れ条件 4 項目に §A〜§D を 1 対 1 で対応させて提案済み。ユーザー確認待ち** (チェックは確定後に付ける)。C#・シーンは未変更。

推奨案の要約 (第 2 版。地点・番号・数値の正本は設計書):

- **A 画面** (決定により、ワープできるのは川辺と奥広場の 2 地点。一覧は 1 列 × 2 行):
  - 地図は「さんぽ」タブの上段 [地図と移動] から開く副画面にする。タブの帯 7 枚は維持する。
  - 北を上に固定した地図に、意味で呼ぶ地点 6 つ (設計書の事実 4) と、自分の現在地・向きを出す。
  - 行き先は右の 2 列 × 3 行から選び、[ここへワープ] の 2 段階にする。
  - 人の一覧は、開いている間は並べ替えず、playerId で持つ。
  - 合流は、相手の受付箱 (VRCPlayerObject) へ申し込む。相手の通知板に名前・場所・[いいよ] / [いまはだめ] を出す。応答は code で分ける (断り / 対応中 / 休止)。通知の間隔は 20 秒。
- **B 同行**:
  - 自分の接続犬 (押した時点の `dogMask`) を全頭連れていく。
  - Manager Owner が、要求 ID 付きの切符を「準備」で書く。本人は、自分の要求 ID を確かめてから TeleportTo する。
  - 犬の Owner は、**飼い主が着地点に来たのを見たときだけ**犬を 1 回置き、経路の状態を初期化して完了を報告する。
  - 本人が移動しなければ、犬は動かない。Phase (準備 / 完了 / 取消) を同期するので、Owner が交代しても復元できる。他人の犬は照合 2 段で動かさない。
- **C 検証**:
  - `KH_CourseWalkHarnessEditor` に travel モード (11 ケース) を足す。遅れた応答・移動前後の Owner 交代の模擬・取消と承認の競合・接続の変更を含む。AI 実行の条件は vrc-verification §1 に従う。
  - 実通信・Owner 交代・途中参加は、PCVR 2〜3 人の 7 手順で確かめる。Quest/iOS・16 人は VER-WLD-001 の回に割り当てる。
- **D 快適さ・失敗時**:
  - 暗転は、黒へ alpha で補間する全画面の板を queue 5001 に置き、黒を描いてから移動する。
  - 着いたときの向きは道の正方向にする (広場だけは古民家の方向)。
  - 着地点の候補には、共通の検査 5 つ (足場・傾斜・頭上・川から 10 m・人から 1 m) をすべて通す。全部だめなら移動しない。
  - クールダウンは、成功後 10 秒 / 失敗後 3 秒 / 同じ相手 30 秒。

調査で分かったこと: 犬の追従テレポートは、犬の Owner 端末で距離 10 m 超 (コード既定値) かつ NavMesh の経路が完全なときだけ起きる。それ以外は 7.2 m/s で走って追う (`KD_DogWanderController.HillsideLeash.cs:306-323,1063-1068`)。フレンド判定は Udon の公開 API に無い (Worlds SDK 3.10.5 の Wrapper DLL で 0 件)。根拠と数値は設計書 §1。独立レビュー (Codex、2026-09-27) の指摘 24 件と対応は設計書の末尾。
