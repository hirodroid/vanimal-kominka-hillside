## 0. 結論 (推奨案の要約)

- **地図は「さんぽ」タブの中の副画面にする。新しいタブは作らない。** タブの帯は古民家と同じ 7 枚・幅の和 1100 ですでに埋まっている ([メニュー再構築計画](2026-09-23-menu-rebuild.md) の 64 行目・188 行目)。world-ui-spec §1 では、配置は古民家と同じにし、変えるのは DES-UI-003 で決めた差分だけ、と決まっている。副画面は、既存の「ポイントの面」と同じ開き方 (`_OpenExtraSettings`、`KD_TreatPouch.Hillside.cs:118`) を流用する。
- **行き先は、意味で呼ぶ地点。初期公開でワープできるのは川辺と奥広場の 2 つ** (決定 2026-09-27)。入口 / 既存広場 / 上流の橋の手前 / 下流の橋の手前の 4 つは候補として残し、地図には目印として描くが、ワープはできない。座標は、周回路のノード (保存済みの足場) から Editor の生成器が決めて検査する。橋の上と川は避ける (§D.3)。
- **合流は、要求する人が申し込み、相手が [いいよ] を押したときだけ、要求した本人が自分で移動する。** 相手を動かす機能は作らない。フレンド判定の API は Udon に無いので、在室しているプレイヤー全員から選ぶ (§A.4、事実 3)。
- **同行の契約は「本人が着いたのを犬の Owner が見てから、犬を 1 回だけ置く」。** 順番は次のとおり。
  1. Manager Owner が要求 ID 付きの切符を「準備」として書く。
  2. 本人は、自分の要求 ID が載ったことを確かめてから、自分を TeleportTo する。
  3. 犬の Owner は、飼い主が着地点に来たのを見たときだけ、犬を着地点の周りに置く。本人が移動しなければ、犬は動かない。
  - プレイヤーの TeleportTo だけに頼らない。
- **暗転はワールド側で作る。** VRChat の TeleportTo には暗転の引数が無い (事実 3)。全画面の黒い板を、ライブの粒子より上の queue 5001 に 1 枚置き、黒になるのを確かめてから移動する (§D.1)。
- **検証は 2 段に分ける。** ClientSim では、既存の周回コース歩行ハーネス (`KH_CourseWalkHarnessEditor`) に travel モードを足し、1 クライアントでの順序と冪等性を確かめる。AI が実行してよい条件は vrc-verification §1 に従う。実通信・Owner 交代・途中参加は、PCVR の 2〜3 人で確かめる (§C)。

## 1. 調査で確かめた事実

### 事実 1: 手元メニューの「さんぽ」と目的地

- 目的地の定義は**シーン上のデータ**で、Editor が生成して書き込む。周回路の `KH_WalkRoute.destinationNodes` は `{0, 16, 0, 0, (215,40,605) に最も近いノード, (505,10,285) に最も近いノード}` (`Assets/KominkaHillside/Scripts/Editor/KH_CourseRouteEditor.cs:108`)。値の意味は、0 入口 / 1 広場 / 2 山道から周回 / 3 川から周回 / 4 奥の広場 / 5 川辺。周回の 2 と 3 は、どちらも門 (ノード 0) を基準にして方向だけを持つ (`KH_WalkRoute.cs` の `_LoopDirection`)。
- メニューの並びは `Destinations={1,0,2,3,4,5}` の 6 行 (`KH_CourseMenuEditor.cs:22`)。ハンドラは `_WalkPlaza` から `_WalkRiverbank` まで、すべて `_` で始まる (`KD_TreatPouch.Walk.cs:65-70`)。ページは 2 列の Grid (508×112) でスクロールし、`WalkRow0..11` (犬 6 行 + 行き先 6 行) が並ぶ。
- 選択は次の順に伝わる。
  1. `_ChooseDestination` がローカルの `_myChoice` を書き、`SendCustomNetworkEvent(Owner, ReqDestination, dest)` を送る。
  2. Manager Owner は `NetworkCalling.CallingPlayer` と `walkers[i]` を照合し、その人の犬の `destinations[i]` だけを書き換えて `RequestSerialization` する (`KH_LeashManager.cs:139-154`)。BUG-DOG-004 のために、Owner 側で `[KH_Leash] ReqDestination ... dogs= changed=` を出している。
  3. 犬をつなぐときは、本人の選択を `ReqAttach` の引数で渡す (`:182-200`)。
- メニュー側の同期変数は 0 本。要求の結果は共有状態をポーリングして確かめ、4 秒で「結果を確認できませんでした」を出す (`KD_TreatPouch.Walk.cs:137-167`)。メニューは開いた瞬間に `PlaceInFront` で目の前 0.95 m に置かれ、その後は動かない (`KD_TreatPouch.cs:1345-`)。
- 途中参加者 (Late Joiner) の扱い: `walkers` / `hands` / `destinations` / `releasedHomes` は Manual の同期変数なので届く。`_myChoice` はローカルなので、再入室すると既定値 (広場) に戻る。

### 事実 2: リード接続の契約と、TeleportTo だけでは追従が保証されない根拠

- **保持**: 1 つの Manual Manager が、犬 6 匹ぶんの `walkers[6]` (接続した人の playerId。-1 は未接続) と `hands[6]` (0 左 / 1 右) を持つ。片手 3 匹の上限は、Owner が裁定するときに数える (`KH_LeashManager.cs:195`)。合計 6 匹は配列の長さで決まる。
- **犬の Owner**: 接続しても Owner は変わらない。犬側では `SetOwner` を呼ばない規律で、`IsDogOwner` は dogRoot の Owner を見る (`KD_DogWanderController.cs:1904-1911`)。通常は、インスタンスマスターが 6 匹すべてと Manager の Owner を兼ねる。ただし Ownership は GameObject ごとに自動で移るので、両者が常に同じ人だとは保証されない。
- **位置の同期**: 犬の Owner だけが dogRoot を書き、`VRCObjectSync` が配る (`KD_DogWanderController.HillsideLeash.cs:12-15`)。非 Owner は、観測した差分から脚の動きを選ぶ (`:279`)。
- **急に離れたとき (現行)**:
  - 手との距離がリード長の 1.25 倍を超えると、Return に入る (`:306`)。リード長はコード既定値 3 m なので、3.75 m。
  - 距離が `catchUpDistance` (コード既定値 10 m) を超えている間は、1 秒ごとに「手の 0.9 m 手前へのテレポート」を試す (`:318-321`)。成功するのは、犬の現在地から目標まで NavMesh の経路が `PathComplete` のときだけ (`:1063-1068`)。
  - テレポートに失敗すると走って追う。リード長の 1.6 倍 (4.8 m) より遠ければ `sprintSpeed` (コード既定値 7.2 m/s)、それより近ければ `dashSpeed` (コード既定値 4.5 m/s) (`:323`、`KH_LeashManager.cs:52-53`)。
- **プレイヤーの TeleportTo だけでは、追従が必ず成立するとは扱わない。根拠は次の 5 つ。**
  1. 犬の再配置は、**犬の Owner の端末で**、次の Return 判定のときに起きる。本人の移動が Owner に届くまでの遅れと、1 秒ごとの再試行の間に、犬は旧地点から走り出す。
  2. 数百 m 離れた 2 点の間で `NavMesh.CalculatePath` が `PathComplete` を返すかは、**まだ測っていない**。失敗すると 7.2 m/s で 2.4 km のコースを追うことになり、実質的には置き去りになる。
  3. 着地点は「手の 0.9 m 手前」の 1 点しかない。6 匹が同じ点に固まる。
  4. `TeleportTo` は `_routeNext` を消すが、`_routeResume` は残す (`:1073`)。周回の再進入では、`_routeResume` が残っていると最寄りノードで代わりに進入せず、3 秒ごとの再試行になる (`:711`)。12 m より遠い移動なら、入口を選び直す保護はある (`KH_WalkRoute.cs:106`)。
  5. 飼い主の速さの推定は、1 フレームで 1 m を超える移動を捨てる (`HillsideLeash.cs:653`)。遠隔側で位置が補間されると 1 フレームの差が小さくなるため、「走っている」と読まれるおそれがある (未確認)。
- **退出と Respawn**: 飼い主が退出すると、Owner が接続を解く (`KH_LeashManager.cs:272-278`)。自動移譲の最中の退出は、`Update` で直す (`:291`)。Respawn には専用の扱いが無い。

### 事実 3: SDK の API (Worlds SDK 3.10.5 で実在を確認)

`Packages/com.vrchat.worlds/Runtime/Udon/External/VRC.Udon.VRCWrapperModules.dll` の extern 名を Node で抽出した。型ごとにどの形があるかは、`VRCSDKBase.dll` の `VRCPlayerApi._TeleportTo` / `_TeleportToOrientation` / `_TeleportToOrientationLerp` の 3 つの委譲と、ClientSim がそれを受ける `ClientSimMain.cs:672-674`・`ClientSimPlayerManager.cs:341-353` で確かめた。

### A.4 プレイヤー一覧と合流

- **取り方**: `GetPlayers` を `OnPlayerJoined` / `OnPlayerLeft` のときに取り直す。行は固定の 16 行で、スクロールする。
- **並びの凍結**: 面を開いた時点の距離順で並べ、**開いている間は並べ替えない**。距離の数字だけを 1 秒ごとに更新する。入室した人は末尾に足し、退出した人の行は消す。押したときの相手は、**行の位置ではなく playerId で持つ**。退出した人を選んでいたら、選択を外して「相手が退室しました」と出す。
- **一人のとき**: 「いまはほかの人がいません」と出し、[地点へ] で地点の画面へ戻れるようにする。
- **行に出すもの**: 表示名 (§A.6) + 「奥広場の近く 35 m」。受け付けを OFF にしている人は、暗くして「申し込みを受けていません」と出す。受付箱がまだ用意できていない人 (入室直後) は「準備中」と出し、押せなくする。
- **地図の目印**: 行を選んでいる間だけ、その人の位置に輪を出す。常に全員を出すのは後回し。
- **要求する側 R の流れ**:
  1. [合流をたのむ] を押すと、`seq` を 1 つ進め、`T の受付箱.SendCustomNetworkEvent(Owner, "ReqJoin", seq)` を送る。
  2. 行の表示は「返事を待っています (20)」+ [取り消す] になる。取り消すと `CancelJoin(seq)` を送る。
  3. `AnsJoin(seq, code)` を受け取る。`CallingPlayer == T` で、`seq` が今保留中のものと一致するときだけ採る。取り消し済みの `seq` の応答は捨てる。
  4. code ごとの扱い:
     - `1` 承認: §D.3 で着地点を決め、§B へ。
     - `2` 相手が別の申し込みに対応中: 「相手はいま別の申し込みに対応しています。少しあとで」と出す。30 秒の待ちにはしない。
     - `3` 受け付けを休止中: 「相手はいま申し込みを受けていません」。
     - `0` 断り、または時間切れ: 「今は合流できないようです」。
- **相手側 T の流れ**:
  1. `ReqJoin` を受けると、T の端末だけに**通知板**を出す。
     - 内容: 「**(R の表示名)** さんが近くに来たいそうです」+ R の場所 (「奥広場の近く」)、[いいよ] [いまはだめ]、20 秒の秒読み、音 1 回、[しばらく受けない (10 分)]。
  2. 通知板は、目の前 1.1 m・視線の 15° 下に置く。T が 3 m 以上歩いたら、目の前に置き直す。T が歩いていても通り過ぎないようにするため。
  3. 手元メニューのさんぽタブの上段にも「申し込み 1 件」を出す。押すと通知板をもう一度表示する。
  4. 保留にできる申し込みは 1 件だけ。2 件目は code `2` を返す。
  5. **通知の間隔**: 前の通知を閉じてから 20 秒は、新しい申し込みに code `2` を自動で返す (別々の人からの通知が続かないように)。
  6. [しばらく受けない] を押すと、10 分間は code `3` を返す。[この人からはこの滞在中は受けない] (通知板の小さなリンク) を押すと、その人にだけ code `0` を黙って返す。どちらも保存しない。
- **設定**: 設定面に「合流の申し込みを受ける」を 1 行足す。受付箱の同期 bool `accepting` で、他の人の一覧にも反映する。

## B. 同行の契約 (受け入れ条件 2)

### B.1 対象と形

| 構成 | 例 | 着地後の配置 (飼い主の向き基準の近似) |
|---|---|---|
| 0 匹 | ひとり | 人だけが移動する。切符は出さない |
| 1 匹 | 左 1 | 左の横 0.75 m・前 0.5 m |
| 3 匹 (片手) | 左 3 | 左の横 0.75 / 1.20 / 1.65 m・前 0.5 / 0.85 / 1.2 m |
| 3 匹 (両手) | 左 2 + 右 1 | 左は段 0 と 1、右は段 0 |
| 6 匹 | 左 3 + 右 3 | 左右とも段 0〜2 |

- 配置は、散歩中の目標 `_WalkingTarget` (`KH_LeashManager.cs:157-176`) と**同じ左右と段の構成を使った近似**。本来の式は手の位置を基準にし、オフセットをリード長 − 0.6 m で切る。着地前は手の位置が分からないので、ここでは「着地点 + 飼い主の向き × 段のオフセット」で置く。着いた後は、通常の散歩の目標へ自然に寄る。揺らぎの項は入れない。
- 各段の点は、`NavMesh.SamplePosition(1.0 m)` で地面に合わせる。取れない点や、段差が 0.6 m を超える点は、着地点へ半分寄せて取り直す。それでも取れなければ、着地点そのものに置く。
- **連れていくのは、ボタンを押した時点での自分の接続犬すべて** (犬の集合 = `dogMask`)。一部の犬だけを連れていく操作は作らない。

### B.2 他人の犬を動かさない条件

1. 切符を書けるのは Manager Owner だけ。書く対象は、書く瞬間に `walkers[i] == CallingPlayer.playerId` で、かつ要求の `dogMask` に入っている犬だけ。`dogMask` と実際の接続犬が一致しないときは、何も書かない (§B.4)。
2. 犬の Owner は、適用する瞬間にもう一度確かめる: `walkers[i] == travelHolder[i]` か。
3. 未接続・集合中・呼ばれて待機中の犬は、接続できないので対象にならない (`KH_LeashManager.cs:184-192`)。合流先の相手の犬は、相手の接続犬なので対象外。
4. 解除 (`Release`) したら、その犬の切符を消す (`travelPhase[i] = 0`)。

### B.3 同期する項目 (Manager、Manual。書くのはすべて Manager Owner)

| 配列 (長さ 6。宣言時に初期化) | 型 | 意味 | 書く時 | 解除・取消の時 |
|---|---|---|---|---|
| `travelReq` | int | 要求 ID (`playerId × 65536 + seq`)。0 は無し | 準備 | 0 |
| `travelHolder` | int | 切符を出した人。`walkers` と照合する (**同期する**。犬の Owner と Manager Owner が別の人でも照合できるように) | 準備 | -1 |
| `travelCenter` | Vector3 | 飼い主の着地点 L | 準備 | そのまま |
| `travelPoint` | Vector3 | その犬の配置点 | 準備 | そのまま |
| `travelYaw` | float | 着地したときの向き | 準備 | そのまま |
| `travelAtMs` | int | 準備した時刻 (`GetServerTimeInMilliseconds`) | 準備 | そのまま |
| `travelPhase` | int | 0 無し / 1 準備 / 2 完了 / 3 取消 | 準備・完了報告・取消 | 0 または 3 |

- 大きさは 6 × (4+4+12+12+4+4+4) = 264 byte で、Manual の上限 (約 274KB) に対して小さい。
- 受付箱 (`KH_TravelMailbox`) の同期は `accepting` の 1 本だけ。手元メニュー・通知板・暗転の同期は 0 本。

- **本人が着地点に来るまで、犬は動かない。** 本人が移動しなかった場合 (取りやめ・失敗・その場に残った) は、手順 6 の条件が成り立たず、犬は通常どおり本人のそばに居続ける。切符は 15 秒で期限が切れる (置き去りにならない)。
- **旧地点へ引き戻さない。** 適用の条件に「飼い主が L から 6 m 以内」があるので、飼い主と歩き出した後 (L から 6 m より遠い) に適用されることは無い。適用しても、手に近い犬は位置を変えない。
- **経路の状態の初期化** (手順 6。位置を変えない場合も必ず行う): `_routeNext = -1`、`_routeResume = -1`、`_arrived = false`、`_nextRouteEntry = 0`、`ResetPauseAndPoseState()`、`ResetHolderSpeed()`、`_leashCorners = null`。`destinations[i]` は変えない。
- **位置を変える処理はここ 1 か所に集める。** 切符が準備 (Phase 1) の間は、同じ犬の Return による追従テレポートを止める (手順 6 の判定を Return より前に置く)。
  - 犬の Owner と Manager Owner が同じ人 (通常の場合): 切符は Owner の端末にもう書かれている。本人が着いた最初のフレームで手順 6 が先に成立するので、位置の変更は**全頭ちょうど 1 回**になる。
  - 別の人の場合: 犬の Owner の端末に、切符より先に本人の位置が届くことがある。そのときは既存の Return が 1 回跳ぶ (手の 0.9 m 手前)。その後に切符が届くと、手に近い犬は位置を変えずに経路の初期化だけを行う。そのため、位置の変更は**全頭 2 回以下**で、最後の位置は飼い主の手の周りになる。検証の合格条件 (§C) は、この 2 つの場合で分ける。
- **Owner が交代したとき**: 切符 (Phase / reqId / Holder / Center) は同期されているので、新しい犬の Owner も同じ条件 6 で判断できる。完了の報告が Manager に届く前に犬の Owner が退出した場合は、新しい Owner から見て Phase 1 のまま残る。飼い主が L のそばにいて、犬も手のそばにいれば、位置を変えずに完了を報告し直すだけになる。「適用済み」をローカルの推測で決める仕組みは使わない。
- **取消**: `CancelTravel(reqId)` を受けたら、Manager Owner は `travelReq == reqId` の犬を Phase 3 にする。取消と承認が行き違っても、要求 ID が違う切符は、どちらの処理も対象にしない。
- **Phase 4 (本人が移動済み、2026-09-28 破壊監査 RC-01 で追加)**: 本人は TeleportTo して着地点 (2 m 以内) に着いたのを一度確かめてから `ReqTravelMoved(reqId)` を送り (Phase 1 の犬が残る間 1 秒ごと。確かめた後の再送は距離によらない)、Manager Owner は送り主の要求 ID・Holder・接続が一致する Phase 1 だけを 4 にする (適用期限はそこから 15 秒。遅延・重複は冪等、取消済みは戻さない)。犬の適用 (手順 6) は「Phase 4 かつ飼い主が L から 6 m 以内」、完了は 4 → 2、取消は 1 → 3 だけ。適用済みの犬の完了の再送は距離によらない (RC-02)。未適用の切符が待ち (Phase 1 か 4、期限内) の間は、飼い主が離れても犬は Return に入らずその場で待つ (本人の TeleportTo から Phase 4 が届くまでの数フレームに 588 m 先へ走り出さないため。期限切れなら通常の Return)。詳細は IMP-WLD-001 段階 1 の「破壊監査の反映」。

- 実装 (2026-09-27): 犬が切符を見るのは 15 秒まで (`TravelTicketLifeMs`)、Manager Owner が準備の切符を Phase 0 に片付けるのは 20 秒 (`TravelExpireMs`)。本人の確認は Phase 1 だけでなく Phase 2 も認める (犬が先に完了していても成立させる)。本人は TeleportTo の直前に共通の検査 5 (人) をもう一度行い、塞がっていれば取りやめる。着いた後は全頭の Phase 2 か 15 秒まで「犬を待っています」と出す。

### B.5 非 Owner からの要求

- `ReqTravel` / `CancelTravel` / `ReqTravelDone` は `[NetworkCallable(maxEventsPerSecond: 2)]`。
- 引数は偽装できる。そのため Owner は次を確かめる。
  - L が `NavMesh.SamplePosition(1.0 m)` で取れること
  - L がコースの範囲内 (x 0〜600、z 0〜720) にあり、川床ではないこと
  - `dogMask` が送り主の接続犬と一致すること
- 人の移動は本人の端末で起きるので、止める必要が無い。検査は「その人の犬をどこに置いてよいか」に限る。
- 同じ犬への新しい要求 ID は、前の切符から 5 秒たつまで捨てる (連打・偽装の連続を防ぐ)。
- 受付箱の `ReqJoin` / `AnsJoin` / `CancelJoin` は、ネットワーク経由で呼ぶので `_` を付けず、`[NetworkCallable]` を付けて `CallingPlayer` と `seq` を照合する。UI のハンドラは、すべて `_` で始める。

- 実装 (2026-09-27): `ReqTravelDone` の上限は 6 回/秒 (1 回の移動で最大 6 匹ぶん届くため。`ReqTravel` / `CancelTravel` は 2 回/秒のまま)。Owner は、送り主の犬に載っている要求 ID (Phase を問わず) より古い番号を捨てる (取消の記録はローカルの 8 件なので、同期済みの配列でも判定する。seq は 16 bit で回るので差が半周未満のときだけ新しいとみなす)。取消済みの要求が遅れて Phase 1 になっても、本人は L へ行かないので犬は動かず、15 秒で期限切れになる。

### D.3 着地点の検査と代わりの点 (全候補に共通)

| 通常 | P から向きの逆へ 3.5 m | その周り (半径 1.5 m の 6 点) → 最寄りのノード | — |
| 歩いている (1.5 m/s 超) | 進行方向の逆へ 5 m の、道のノード | その前後のノード | 「相手の少し後ろに着きます」 |
| 橋の上 | **相手が向かう岸**の手前のノード (進行方向から判断。止まっていたら R から近い岸) | 反対の岸 | 「橋の手前に着きます」 |
| 川床・水中 | 30 m 以内の最寄りのノード | その前後のノード | 「川の近くなので、岸の道に着きます」 |
| 道から遠い・コースの外 | 30 m 以内のノード | — | 無ければ移動しない。「相手の近くに安全な場所がありません」 |

- **地点 ID の解決**: Editor の生成器が、地点 ID ごとの基準座標から最寄りのノードを引く。ワープできるかどうかは、地点ごとの `spotWarpEnabled` で持つ (初期公開では upper と river だけ true。2026-10-03 IMP-WLD-004 で gate〜river の 5 つが true、bridgeDown だけ false)。地点を足すときは、この値を変えて再生成するだけでよい。上の共通検査の 1〜4 (人の検査を除く) を通したものを、Manager の静的配列 `spotPositions` / `spotYaws` に書く。Verify は、保存後に同じ検査をもう一度行う。経路を作り直したら、生成器を再実行する。

### D.4 相手が退出したとき

| 段階 | 扱い |
|---|---|
| 申し込み中 | `OnPlayerLeft` で取り消し、「相手が退室しました」 |
| 承認の後、確認の待ち (手順 4) の間 | 取りやめ (`CancelTravel`)。移動しない |

### D.5 連打とクールダウン (推奨値。Play で決める)

- 移動に成功したら 10 秒、取りやめ・失敗の後は 3 秒。残りの秒数は [ここへワープ] に出す。
- 同じ相手への申し込みは、断られるか時間切れになってから 30 秒あける (code 2 / 3 はこの対象外)。
- 相手の側の通知の間隔は 20 秒 (§A.4)。Owner の側は、同じ犬に 5 秒 (§B.5)。
- 処理中は、要求を 1 本だけ持つ。

### D.6 誤操作対策

- 地点ワープ: 確認のモーダルは置かない。「セルを選ぶ → [ここへワープ]」の 2 段にし、フッターに連れていく犬の数と着いた後の行き先を出す。
- 合流: 相手の同意が要るので、確認は不要。R は申し込み中と暗転中に取り消せる。
- 犬がボールやディスクを追っている間は、移動できない (「ボールを追っている犬がいます。戻ってから」)。Fetch やフリスビーの最中は、リードが位置の制御を渡している (`HillsideLeash.cs:211-217`) ので、適用する時点が決まらないため。

### D.7 ワープの役割と、散歩を続ける / 入口へ戻る

- **役割** (推奨): 歩く散歩の置き換えではない。**合流・短い散歩・帰還を助けるもの**として扱う。「ワープした後に歩き出すか」を PCVR の評価の項目に入れる (§C.2 §0)。どの範囲で使えるようにするかは、ユーザー判断 1。
- 散歩を続けるとき: `destinations` は変えない。フッターに「着いたら: 行き先『山道から周回』のまま」と先に出す。着いたら [さんぽへもどる] で、行き先や周回の向きを選び直せる。
- 入口へ戻るとき: ①へワープする。犬は一緒に来る。[はずす] と、道具は入口の拠点へ戻る (既存の規則)。**古民家ワールドへ帰る導線は DES-WLD-001 で扱う。**
- VRChat の Respawn: 切符が無いので、既存の Return に任せる。後から切符を出す案 (`OnPlayerRespawn`) は後回しにする。

## F. 呼ぶ (2026-09-29 ユーザー要望)

### F.1 決定 (2026-09-29)

- ユーザー要望「合流だけじゃなくて、呼ぶのも欲しい」。**1 人を呼ぶ** (複数人を一度に呼ぶことはしない)。決定: 2026-09-29 (ユーザー)。

### F.3 通信

**入口は `ReqCall(int seq)` を別に足す** (第 1 版の「`ReqJoin` に kind を足す」は取り下げ)。決定: 2026-09-29 (Codex 相談)。同じインスタンスに異なる版のワールドが同居しうる (公式 Network Compatibility) ので、既存の `ReqJoin(int)` の署名は変えない。

| メソッド (`[NetworkCallable(maxEventsPerSecond: 2)]`、`_` なし) | 役割 | 照合 |
|---|---|---|
| `ReqJoin(int seq)` (今のまま) | 合流の申し込み。`Receive(送り主, seq, 合流)` へ | 箱の Owner の端末だけ・送り主 = `CallingPlayer`・自分からは捨てる |
| `ReqCall(int seq)` (新) | 呼ぶ。`Receive(送り主, seq, 呼ぶ)` へ | 同じ |
| `AnsJoin(int seq, int code)` (今のまま) | 返事 (両方の種類) | 送り主 == 保留中の相手 かつ `seq` == 保留中の `seq` |
| `CancelJoin(int seq)` (今のまま) | 取消 (両方の種類) | 送り主 + `seq` が、T の保留中・T の「呼ばれて移動中」のどちらかと一致 |

- ネットワークから呼べるのはこの 4 つだけ (Course/81 が名前と署名を照合する)。照合・冪等・差し替え・交差は 1 つの非公開処理 `Receive` に書き、2 か所に分けない。受付の間隔・休止・拒否は種類をまたいで共通。
- 旧版の端末へ `ReqCall` を送ると返事が来ない。R はそれを「断られた」ではなく「結果を確認できませんでした」と出す。
- code: 0 断り / 1 承認 (合流) ・到着 (呼ぶ) / 2 対応中 / 3 休止中 / **4 準備中 (呼ぶ)** / **5 移動の前に止まった (呼ぶ)**。既存の合流の code 1 = 承認は変えない。種類を `seq` に埋め込まない。
- ローカル専用 (すべて `_` 始まり): `_RequestJoin(id)` / `_RequestCall(id)` (共通の `_Request(id, kind)`)、`_AnswerYes/No/Go/NotNow` と世代つきの `_AnswerYesGen(gen)` など、通知板の `_Yes/_No/_Go/_NotNow/_Pause/_Block`、手元メニューの `_TravelGo` / `_TravelCall`。

**`seq` と終わった要求** (決定: 2026-09-29 (Codex 相談)):

1. R の `_outSeq` は種類に関係なく 1 本の数で進み、R が同時に持てる申し込みは 1 件だけ。R は `(_outTo, _outSeq, _outKind, _outPhase)` を組で持ち、返事の種類はこの組から決まる。
2. T は送り主ごとに「見た最大の `seq`」を覚える。`Receive` と `CancelJoin` はどちらもこれを進め、**`seq` が見た最大以下の要求は捨てる** (古い `seq`・同じ `seq` で種類が違うもの・取消の後に遅れて届いた要求が復活しない。イベントはレート制限で追い越されることがある)。退室した人の記録は `OnPlayerLeft` で消す。
3. 保留中の送り主から新しい `seq` が届いたとき: 同じ種類なら「同じ相手・同じ行為への同意を続ける」として `seq` だけ引き継ぐ (通知の置き直し・期限の延長はしない。今と同じ)。種類が違えば**差し替え**: `seq`・種類・期限・世代を新しくし、通知板のボタン実体を切り替える。古い世代への押下は捨てる。

**交差** (同じ 2 人が互いに申し込んでいる。種類を問わない)。決定: 2026-09-29 (Codex 相談):

- 受けた側が、送り主との移動を**確定済み** (送り主の呼ぶに [行く] で移動中 / 送り主への合流が承認済み / 送り主から準備中を受けた呼ぶ) なら、確定した方を優先して届いた要求に code 2。
- どちらも**未確定** (自分の申し込みが返事待ち) なら playerId の小さい方が勝つ。小さい側は届いた要求に code 2。**大きい側は、自分の申し込みをその場で失効させて相手へ `CancelJoin` を送り**、失効を「相手からの申し込みを先に表示します」と出してから、勝者の要求を通知板に出す。失効した `seq` への遅い返事は捨てる (保留中の `seq` と一致しない)。
- 判定の順: 休止・OFF → 3、その人だけ → 黙って 0、確定済みの交差 → 2、別の保留あり・閉じてから 20 秒 → 2、未確定の交差。別の保留があるときは交差の前に code 2 になるので、両方とも対応中で 0 件になることがある (許容)。

**取消の境界** (決定: 2026-09-29 (Codex 相談)): 取消が勝つのは、**T が実際に移動する前に、T の端末で `CancelJoin` を処理した場合**だけ。T の「呼ばれて移動中」(測定待ち・切符待ち・暗転中) に一致する `CancelJoin` が届いたら、T は移動を取りやめて明るく戻り「{0} さんが取り消しました」と出す。R が暗転中に押しても、届く前に T が移動していれば T は着く。期限後の移動を厳密に止める共通時刻の期限は入れない。

### F.5 同期・途中参加・Owner

- **新しい同期変数は無い。** 同期は受付箱の `accepting` 1 本のまま。種類・保留・世代・見た `seq`・測定・移動中の状態は、すべて箱の Owner のローカル。交渉はネットワークイベントだけで、Late Joiner には届かない。届く必要も無い: 保留は 2 人の端末にしか無く、どちらかが退室すれば `OnPlayerLeft` で片付く。
- 途中参加した人: 箱が作られる前は「準備中」で、呼ぶことも呼ばれることもできない (今と同じ)。
- Owner: `VRCPlayerObject` の複製の Owner = その人。すべての処理は `Networking.IsOwner(gameObject)` の端末だけで動く。`SetOwner` は呼ばない。T の移動の切符は、T の端末から Manager Owner へ出す今の経路 (§B.4・§B.5) をそのまま使う。**T が Manager の Owner でない場合** (実機の通常) の経路は ClientSim では通らないので、PCVR #10 で見る。

## やらないこと

- 相手を強制的に移動しない。フレンド判定を前提にしない。
- 他人の犬・未接続の犬を移動しない。一部の犬だけを連れていく操作は作らない。
- 通常の犬の追従 (Return と追従テレポート) の値は変えない。切符が準備中のときだけ止める。
- ワールド間の移動と、状態の引き継ぎ (DES-WLD-001)。現地の地図板 (DES-UI-004)。
- 犬の Owner を移さない (犬の側で `SetOwner` を呼ばない)。
