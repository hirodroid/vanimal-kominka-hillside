## 決定の反映 (2026-09-27)

ユーザー回答 (音声の要旨):「水遊びは泳ぐことを求める。小さい犬種は泳ぐ。大きい犬種はチャプチャプ普通に入っていくでいい。クリップは作ってもらっているが、走る・歩くのアニメーションで十分泳いでいる感が出ると思う。どうせ犬かきなので、浮いて、ちょっと歩いている感じで動けば十分雰囲気は出る。あとは推奨で OK」。

- 初期公開は推奨どおり、前提 + 段階 0 + 段階 1。水遊び場は 1 か所 (「川辺」脇の東岸の曲がり)、リードを外した犬だけ。段階 2 (浮くボールの回収) は後段。
- **小型犬 (ポメラニアン・コーギー・ダックスフンド) が泳ぐ。柴犬は試作で確かめる。大型犬 (サモエド・ラブラドール) は浅瀬をチャプチャプ歩くだけ。淵は掘らない。**
- **専用の泳ぎクリップは初期公開では作らない。** ルートの高さを水面基準にして浮かせ、既存の歩き / 走りのクリップを再生する。
  - Issue 冒頭の「走りのクリップ流用だけで泳ぎ完成とはしない」は、この決定で上書きした。
  - 見え方が足りないときは、これまでどおり生成で作る (購入・外注はしない)。
  - 18 本のクリップと新しい State `Wade` / `Swim` / `SwimIdle` は、後で必要になったら作る。
- 浅瀬で跳ねる動きと身震いは、既存のクリップと PhysBone の減衰ロールで出せる範囲だけにする。
- レビュー済みの契約は変えない: 復旧 3 段 (C の 6・6b)、`waterPose`、水中 Fetch の保持と解放、先読みの切替。

節の対応: 受け入れ条件 1 → [A](#a-段階と実装範囲)、2 → [B](#b-状態遷移と再現手順)、3 → [C](#c-沈む浮きすぎる取り残す条件)、4 → [D](#d-検証条件と予算)。

### 0-3. クリップと Animator

- **購入アセット (`Assets/TORINOSUKE/`) に泳ぎ・水のクリップは無い。** `swim|oyo|mizu|水|泳|float` のファイル名は 0 件。FBX 6 本 (`犬ギミック/{もちぽめ,コーギー,サモエド,ダックスフンド,ラブラドール,柴犬_remake}/*.fbx`) は `.anim` を分けて持つ。

### 0-4. 犬の移動・状態・同期 (コードの読み取り)

- **NavMeshAgent は使っていない。** 移動はすべて自作で、ルートを書くのは犬の Owner だけ。自由行動 (`WanderTarget` へ) と **Fetch の追跡・持ち帰りは直線移動で経路の確認が無い** (`Imported/KominkaDogRun/Scripts/KD_DogWanderController.cs:1601-1614`、`KD_DogFetchController.cs:903-946, :1036-1044`)。NavMesh を使うのはリード散歩と集合だけ (`KD_DogWanderController.HillsideLeash.cs:1079-1112, :1118-1138`)。
- **高さは下向きレイ `SnapToGround`** (開始 +0.5 m、長さ 4 m、層 0|11、トリガー無視)。外れたら高さを変えない (`KD_DogFetchController.cs:1273-1282`、`KD_DogWanderController.cs:1956-1963`)。水面に Collider が無いので、**水の上ではレイは河床に当たる**。
- 実行時スクリプトに水・川・浮力の概念は無い (水の器の休憩だけ。`KD_DogWanderController.Rest.cs:56-152`)。
- Animator の書き手: Wander が `Walk/Run/LookAt/Pickup/Sit/LieDown` と `Animator.speed`、Fetch が `Walk/Run/Pickup`、Frisbee が `Walk/Run/Jump/Twist/Pickup` と speed。Fetch / Frisbee が動いている間 Wander は `YieldAnimator()` で自分の Bool と speed を降ろす。姿勢の Bool は一度に 1 つ (`HillsideLeash.cs:24, :677-691`、`KD_DogWanderController.cs:1737-1760`)。
- 優先順位 (Wander の Update): リード → Candy → Fetch/Frisbee 中は Wander が退く → 睡眠 → ライブ → Activity → おやつ → Nudge → 休憩・自由行動 (`KD_DogWanderController.cs:1280-1460`)。リードの `leashMode` (Walk 0〜Stopover 8) は Owner のローカルで同期しない (`HillsideLeash.cs:26-29`)。
- Fetch の状態は Idle 0 / ChaseStart 1 / Chase 2 / Pickup 3 / Return 4 / Drop 5 (`KD_DogFetchController.cs:189-194`)。リード中・フリスビー中・睡眠・ライブ中は始めない。Fetch 中にリードが付いたら `GiveUp` (:812-842)。リードの接続は Fetch 非 Idle・集合中・フリスビー中・片手 3 匹で拒否 (`Assets/KominkaHillside/Scripts/KH_LeashManager.cs:192-197`)。
- 同期: `KD_DogFetchController` は Manual で `int dogState / attentionPlayerId / targetObjectId / petState` 等 (`:48, :241-255`)。`KH_FrisbeeCatch` は Manual で `state / throwerId / animSpeed`。`KH_LeashManager` は Manual で `walkers[6] / hands[6] / releasedHomes[6] / destinations[6]`。Wander・ToyRecall・WalkRoute は同期 None。**犬の Owner は SetOwner しない (実質インスタンスの Master)**、位置は犬ルートの `VRCObjectSync`。
- 途中参加: Fetch は `OnDeserialization` → `ApplyState` で Animator・撫で・`pickupable` を戻す (`KD_DogFetchController.Owner.cs:173-272`)。Owner 交代: 対象プレイヤーが居なければ `GiveUp` (`KD_DogFetchController.PetSync.cs:282-316`)。
- ボール: Rigidbody (質量 0.2、drag 0.05、重力あり、連続衝突)、層 13、`VRC_Pickup` + `VRCObjectSync`、`KD_BallController` は NoVariableSync (`KD_Ball_Shiba.prefab:327-345`、`KD_BallController.cs:18-25`)。**持ち帰りは親子付けせず、`LateUpdate` で毎フレーム `mouthAnchor.position` へコピー** (`KD_DogFetchController.cs:1284-1297`)。持ち帰り中は `SetKinematic(true)`。
- ボールの復旧: 追跡 16 s・持ち帰り 20 s のタイムアウトで `GiveUp` し、その場に放す。1 フレームで 2 m を超える移動は追跡を中止する (`KD_DogFetchController.cs:204-216, :1067-1111`)。落下は `VRCObjectSync` の復帰 (シーンの `RespawnHeightY` -10) だけ。置き場 `KH_Dogs/KH_ToyPark` へ位置だけで戻す仕組みは IMP-DOG-019 (`KH_ToyRecall.cs:20-27, :269-282`)。
- 停滞の汎用検知は無い。流用できるのは、リードの 10 m 超え復帰 `TeleportTo` (NavMesh の完全経路が条件、`FlagDiscontinuity`。`HillsideLeash.cs:315-322, :1062-1076`)、集合の「経路が無ければ直進」、各タイムアウト、非 Owner の 1.5 m/フレーム ワープ判定 (`KD_DogWanderController.cs:1923-1944`)。
- 負荷: 6 匹 × (Wander + Fetch + FrisbeeCatch + Pet) の Update が全クライアントで動く。移動中の Owner は 1 歩 1 レイ。リード中は 0.35 s ごとに `CalculatePath` (`HillsideLeash.cs:1078-1092`)。

### 0-5. ここから分かる設計上の結論

1. **B-2 の試作条件 (泳ぎに入る 0.75 M) では、今の川 (最深 0.40 m) でラブラドール (0.42 m) は泳がず、サモエドは中央の幅 2.1〜3.8 m だけで泳ぐ。** 係数 0.75 は未検証の試作値。**決定 (2026-09-27): 淵は掘らず、大型犬 (サモエド・ラブ) は浅瀬だけ、泳ぐのは小型犬**。代表犬 (ポメラニアンと柴犬) で姿勢と切替を確かめ、係数を決め直してから、コーギー・ダックスへ広げる (D-5 の順 3・4)。
2. **既存の直線移動にはすでに穴がある。** 水面に Collider が無く、`SnapToGround` のレイは河床に当たる。そのため、ボールが川へ入ると Fetch の犬は河床を歩いて追い、ポメ〜柴 (M 0.16〜0.36 m) は 0.40 m の水に頭まで沈む経路がある (コード上の推定、実機未確認)。集合の「経路が無ければ直進」も川を横切り得る。水面が不透明なので、沈んだボールと犬は外から見えない。水遊びより先に塞ぐ (前提作業)。
3. 道は川から 11〜29 m 離れ、リードは 3 m。**リード中の犬は、道を外れて岸まで行かないと水に届かない。** 水遊びは岸の「水遊び場」で、リードを外して遊ぶ形が自然。
4. 水面は波が無く平らで、z 方向に傾いているだけ (水面 y は z だけの関数)。浮く高さは「その z の水面高さ」の関数 1 本で決まる。

**`KH_RiverData`** (同期 None): 生成式 `RiverAt` / `HalfWidth` を z 1 m 間隔で焼いた配列 (中心 x・水面 y・半幅、721 × 3 個の float)。Editor の Build が書き、Verify が水面メッシュの頂点と照合する。Udon へ生成式を移植せず、配列を線形補間で引く。

**`KH_WaterSpot`** (同期 None、1 か所に 1 つ): 次のものを持つ。
- 領域 (多角形)
- 入水点・出水点 (岸の NavMesh 上)
- 岸側の復帰点 (出水点ごとに 1 つ。NavMesh 上で、目的地「川辺」の通過点から完全経路があることを Editor で検査済み)
- 0.5 m 格子の河床高さ (8 × 12 m なら 17 × 25 = 425 個)

水中は NavMesh を使わず、領域の中だけで直線移動する。**河床の NavMesh 除外は変えない** (Issue の「全面解除しない」)。

**`waterPose`** (同期 1 個・犬ごと): 0 陸 / 1 浅瀬 / 2 泳ぎ。犬の Owner が切り替えたときだけ送る。置き場所は、同じ Owner の Manual の `KD_DogFetchController` を第一候補にする (犬ルートは `VRCObjectSync` で Continuous のため、同じ GameObject に Manual の変数は置けない)。

- **なぜ位置から導かないか (レビュー M-高)**: 泳ぎ ⇄ 浅瀬のヒステリシス (0.6〜0.75 M の帯) は、過去に泳いだかどうかで姿勢が変わる。途中参加者はその履歴を持たないので、位置だけでは同じ姿勢を一意に復元できない。
- 泳ぎのルート高さ (水面 + c − Ms) と、浅瀬のルート高さ (河床) の差もポメでは数 cm しかなく、判別に使えない。

同じ理由で、リードの接続裁定 (Manager の Owner) も水遊び中かを `waterPose` ≠ 0 で知る。Owner ローカルの `WaterPlay` は裁定側から見えないため。

### A-3. 水遊び場の場所と淵 (決定 2026-09-27: 候補 1、淵なし)

勾配は水面 y の z 方向の変化率 (dy/dz)。川が z 方向へ流れる所ではほぼ流路の勾配になり、斜めに流れる所では上限値になる。

- 候補 1 (推奨): **目的地「川辺」(505, 10, 285) の西、東岸の外側の曲がり**。
  - 既存の目的地・休憩点なので、散歩の途中で寄れる。道からの距離は約 20 m、橋から約 95 m。
  - 勾配は曲がりの前後で 4.6〜5.0 % で、検査の上限 5 % の境目にある。領域は曲がりの頂点 (z 285) の前後 6 m 以内に収める。浮いた犬・ボールが坂を上り下りして見えないかは Play で確かめる。
- 候補 2: 下流の橋 (z 190) より下流の z 115〜170。
  - 勾配は 2.3〜3.6 % で候補 1 より平らだが、道から約 25 m 離れる。
  - 橋の寄り道禁止範囲 (z ±8 m) を避けるため、z 170 以下にする。
- **「川辺」到着から水遊び場への誘導** (レビュー X-中):
  - 入水点は「川辺」の通過点から 12 m 以内に置く。
  - 通過点から岸の入水点まで、Terrain の塗りだけで踏み分け道を描く。容量は増えない。
  - 現地の看板・名前の表示は [DES-UI-004](../development/issues/DES-UI-004-walk-destinations-and-boards.md) で扱う。本書では「通過点から入水点が見える・道が続いている」までを条件にする。
- **淵は掘らない (決定 2026-09-27)。** 検討した案: 水遊び場の中だけ河床を中心 0.65 m まで下げ、ラブ・サモエドも泳げるようにする。ユーザー判断は「大型犬は普通にチャプチャプ入っていくでいい」だったため、今の川の深さのままにする。
- 淵が無いので、試作条件ではサモエドも中央で泳ぎの深さに届くが、**泳ぐ犬種から外し、浅瀬の歩きのままにする** (B-2)。「6 匹とも泳ぐ」は求めない。

## B. 状態遷移と再現手順

**タイムアウトと泳ぐ速さ (レビュー X-中)**: 既存の追跡 16 s・持ち帰り 20 s は陸の走りの値で、泳ぎには短すぎる。

- 8 × 12 m の領域の対角は 14.4 m。ポメで片道 34 s かかり、既存の 16 s では足りない。

- 計時の始まりは入水時 (6) と、くわえた時 (7)。上陸したら既存の Return の 20 s を上陸時から数え直す。
- 投げた人が対岸・遠く (手元への陸の経路が NavMesh で完全でない) なら、犬は入った岸の復帰点で Drop する。ボールは陸に残る。

**始め方の案内 (レビュー U-高)**: 入水・再接続の規則は、画面に手掛かりが無いと故障と区別しにくい。

### B-2. 犬種別の入水・浮遊の切替条件

水深 `d` = 水面の高さ (`KH_RiverData`) − 河床の高さ (`KH_WaterSpot` の格子)。犬のルート (足元) の (x, z) で引く。切替は Owner が決め、`waterPose` で配る。

- **次の 1 歩の位置で先に d を引く (レビュー U-高)**。
  - 深くなる向き (陸 → 浅瀬 → 泳ぎ) は、次の 1 歩で条件を満たした時点で**即時**に切り替える。待ち時間は置かない。
  - 待ち時間の 0.5 s は、浅くなる向き (泳ぎ → 浅瀬) にだけ置く。
  - これで、浅瀬を歩く間の口と水面の差は常に 0.25 M 以上 (ポメで 0.039 m) を保つ。
- **即時に止める条件**: 次の 1 歩で口 − 水面 < 0.03 m になるなら、その歩を進めない。泳ぎへの切替か、引き返しを先にする。
  - 格子の外・格子の値が壊れているときに起きる。本来は起きない。
  - 起きたら Owner ログへ `reason=sink-guard` を出す。

| 区分 | 条件 (M = 口の高さ) | 見え方 |
|---|---|---|
| 足が濡れる | d > 0.02 m | しぶき FX・小さい水音 (段階 0) |
| 浅瀬 (`Wade`) | 0.02 m < d かつ 泳ぎでない | 歩き。d > 0.3 M で速さを歩きまでに制限。段階 1 では止まったときに前足で跳ねる |
| **泳ぎに入る** (泳ぐ犬種だけ) | 次の 1 歩で d ≥ 0.75 M (即時) | 既存の Walk / Run を再生したまま浮かせる (止まっている間も Walk を低速で再生して漕ぎ続ける)。ルートの高さを河床ではなく水面から決める |
| **泳ぎから足をつく** | d < 0.6 M が 0.5 s 続いた | 浅瀬へ戻る (0.15 M のヒステリシス) |
| 泳ぎの高さ | ルートの y = 水面 + 余裕 c − `Ms` | `Ms` = **歩きクリップ (`Walk`) での口の高さ** (決定 2026-09-27 で専用クリップは作らない。実装時に facts として測る。立ったときの M とほぼ同じ見込み)。c = 0.04 m、**ボールをくわえている間は 0.06 m** (ボールの半径 0.043 m より上に口を出す) |
| 河床への食い込み | 歩きクリップを浮かせると、足は水面から約 M − c の深さまで伸びる。d < M − c では足先が河床の下へ入る | **水面が不透明なので、水面より下は見えず問題にしない** (River Lite は不透明・ZWrite)。泳ぎ → 浅瀬へ戻るときのルートの持ち上がり (最大 M − c − 0.6 M) は 0.3 s で補間する |
| 上下の揺れ | ±0.01 m・0.8 Hz | ルートではなく見た目の子 (メッシュ側) に、全端末でローカルに足す。ルートを書くのは Owner 1 人のまま (`vrc-networking` §8) |

| 犬 | M | 浅瀬で速さ制限 (0.3 M) | 泳ぎに入る (0.75 M) | 足をつく (0.6 M) | 今の川で泳げる帯の幅 (半幅 1.75 / 2.6 / 3.42 m のとき) |
|---|---:|---:|---:|---:|---|
| ポメラニアン | 0.157 | 0.047 | 0.117 | 0.094 | 3.8 / 5.0 / 6.1 m |
| コーギー | 0.228 | 0.069 | 0.171 | 0.137 | 3.5 / 4.6 / 5.7 m |
| ダックスフンド | 0.230 | 0.069 | 0.172 | 0.138 | 3.5 / 4.6 / 5.7 m |
| 柴犬 | 0.359 | 0.108 | 0.269 | 0.215 | 3.0 / 4.0 / 5.0 m |
| サモエド | 0.503 | 0.151 | (泳がない) | — | 浅瀬のみ (決定 2026-09-27)。深さ 0.40 m で口の余裕 0.10 m |
| ラブラドール | 0.556 | 0.167 | (泳がない) | — | 浅瀬のみ (決定 2026-09-27)。深さ 0.40 m で口の余裕 0.16 m |

- 帯の幅は生成式の断面から計算した値 (岸の非対称 ±1.15 m は含まない)。
- 係数 0.75 / 0.6 / 0.3 と c・`Ms` は試作値。代表犬 (ポメ・柴) の Play で決め直してから、コーギー・ダックスへ広げる。**柴犬を泳がせるかは、この試作で決める** (泳がせない場合は大型犬と同じく浅瀬のみ)。
- 泳がない犬種は `waterPose` 2 にならない。浅瀬の歩きでも B-2 の「即時に止める条件」(口 − 水面 < 0.03 m の歩は進めない) は同じく効く。

### B-3. 再現手順

**Editor の静的検査** (新規 `Tools/KominkaHillside/Water/…` の Verify。AI が実行できる)

1. `KH_RiverData` と水面メッシュ 24 区間の頂点を照合 (水面 y の差 ≤ 0.01 m、中心 x の差 ≤ 0.05 m)。
2. 水遊び場の河床格子と、保存 Terrain の `SampleHeight` の差 ≤ 0.01 m。
3. 入水点・出水点・復帰点が NavMesh 上 (`SamplePosition` 0.3 m) にあり、河床の除外の外側にある。復帰点は、目的地「川辺」の通過点から `PathComplete`。入水点は通過点から 12 m 以内。
4. 領域が橋の禁止帯 (x ±18 m・z ±8 m) と重ならない。水面の勾配 (dy/dz) ≤ 5 %。
5. 犬種ごとに「泳ぎに入る」帯の幅 ≥ 2.5 m (泳ぐ犬種だけ。淵は掘らない)。出水点の岸の傾き ≤ 25°。領域の中の格子を、各出水点へ直線で結べる (石の Collider に当たらない)。
   - 変更 (決定: 2026-09-27、淵を掘らない決定による): 泳ぐ犬種の合格条件は「泳げるセル (0.75 M 以上) が 1 つ以上」とする。帯の幅 2.5 m は記録だけにする。実測 (Course/77) はコーギー 2.21 m・ポメ 2.38 m・ダックス 2.21 m・柴 1.875 m。
6. 除外の縁で水面下に入っている点を数えて一覧にする (0-1 の推定の確認)。

**ClientSim ハーネス** (新規。`KH_CourseWalkHarnessEditor` と同じ型で、期限・停止・PlayerData の退避と復元を持ち、シーンを保存しない)

- 新しいハーネスを AI が実行してよいかは、フリスビーのハーネスと同じく、ユーザーの許可を CLAUDE.md に足してから。
- **判定は毎フレーム行う (レビュー M-中)**。区間ごとに次を集計して出す。ログの出力だけ 0.5 s ごとに間引く。
  - 口 − 水面の最小値
  - 足 − 河床の最小値
  - 1 フレームの最大移動量
  - 違反のフレーム数
  - 状態の遷移回数
- 0.1 s ごとの標本では「全フレーム」「位置の飛び 0」を示せないため。

### D-3. 容量の予算 (見積り)

現在の代理容量は Android 44.83 MiB / iOS 44.01 MiB ([autumn-polish.md](des-env-002/autumn-polish.md#確認結果))。これは保存シーンの代理ビルドの値で、SDK の配信容量ではない。単価は [ビルドサイズ監査](2026-09-24-build-size-audit.md) の実測 (犬のアニメ 134 本 176 KB、自作アニメ 12 本 18 KB、SE 14 本 351 KB) から取った。

| 追加 | 数 | 見積り |
|---|---|---|
| 泳ぎのクリップ | **作らない** (決定 2026-09-27。既存の Walk / Run を使う) | 0 |
| 水しぶき・波紋 FX | Particle 2 種、共有テクスチャ 128² 1 枚 | 10〜30 KB |
| 水音 | 3 本 (小・大・犬かき、モノラル、短い) | 60〜150 KB |
| データ (`KH_RiverData`、格子) | 2 本 | 数 KB |
| 踏み分け道 (淵は掘らない) | Terrain の塗り | 0 (解像度は変えない) |
| **合計** | | **約 0.07〜0.18 MiB** (クリップを作らない分、前回の見積り 0.1〜0.36 MiB から減った) |

**予算の上限は +0.5 MiB (Android 45.3 MiB 程度) を案とする。** 超えたら音 → FX → クリップの順に見直す。音源は削らない方針 (2026-09-24 ユーザー決定) なので、音は本数で抑える。

### D-4. Udon と描画の負荷

- 水の判定は、犬が水遊び場の範囲 (AABB) に居るときだけ格子を引く。範囲の外は、前提作業の川の帯の判定で 1 歩に 1 回、配列を引くだけ。新しいレイは増やさない (水中の高さは格子で決まる)。
- ボールの浮きは、ボールの Owner だけが、ボールが川の帯の中にあるときだけ計算する (6 個まで)。
- 非 Owner は姿勢を `waterPose` から選ぶので、格子は引かない。しぶきの出る位置だけ、0.1 s ごとに d を 1 回引く (水遊び場の範囲に居る犬だけ)。
- しぶき・波紋は各端末のローカル。見る人から 20 m 以内だけ出し、同時に最大 6、1 つ 20 粒子まで。音は同時に 2 本まで。
- 懸念: 6 匹 × 既存の 4 スクリプトの Update に水の分岐が足される。
- **段階 1 の公開判断に使う計測**は game-design §3 の条件に合わせ、[IMP-ENV-004](../development/issues/IMP-ENV-004-river-loop-course.md) / VER-WLD-001 の周回コースの計測と同じ回にまとめる。
  - 16 人参加・犬 6 匹が水遊び場で遊んでいるとき。
  - 集合時 (水遊び場に人が集まる) と、区画に分散したときの両方。
  - 端末・画質・アバター表示条件を記録する。
  - 水遊び場に 6 匹が泳いでいる / いないを並べる。
- Editor の計測 (`vrc-performance` の手順で 2 回ずつ、描画コールとフレーム時間の中央値) は事前の目安にとどめ、Quest/iOS の fps に読み替えない。
