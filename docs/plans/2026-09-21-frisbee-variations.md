## 設計判断 (段階 3、2026-09-21。Play で見直す)

### プリセット = 1 つの同期 int

`KH_FrisbeeCatch.variant` (`[UdonSynced]`, Manual) にプリセット番号を持つ。**比べたいのはプリセットの列**であって軸の組合せ表ではないので int 1 つ。本設定を決める段になったら番号を軸へ分解する。

| v | 名前 (メニュー表示) | 内容 |
|---|---|---|
| 0 | 通常 | 段階 2 の比較基準。**Build Scene が毎回 0 を書く** (新規インスタンスの初期値は通常。途中参加者は現在の同期値に従い、参加を理由に 0 へ戻さない) |
| 1 | 走り込み: 横 | Ready を線の横に置き、横から走り込んで横切って取る |
| 2 | 走り込み: 遠く | Ready を着地点の手前・やや横に置き、正面から向かって来て取る |
| 3 | 走り込み: 並走 | Ready を投げ手の斜め前に置き、前を向いて待ち、後ろから追いついて取る |
| 4 | ひねり | 通常の Ready + ひねりクリップ (空中で up 軸に 90° ひねって取る) |
| 5 | 横曲がり | 通常の Ready + 横向きの揚力で右へ曲がる飛行 (線・飛行・予測は同じ閉形式) |

- 同期する理由: 計画は犬 Owner が実行するが投げるのは誰でもよく (2 人試験で投げ手 ≠ Owner が普通)、ひねりは Animator の Bool を全クライアントが書き、横曲がりは投げ手が飛行を刻む。途中参加者は Manual 同期の現在値を受け取る。
- 変更の入口: `_RequestVariant(v)` (ローカル) → Owner なら `ReqVariant(v)`、他は `SendCustomNetworkEvent(Owner)`。`ReqVariant` は範囲検査し、**Engaged (追走〜持ち帰り) 中は `pendingVariant` (同期) に予約して Idle 復帰時に適用**、Ready 中は即適用 (目標を取り直す)。予約は後の要求が勝ち、現在の番号を要求すると取消。`variant` / `pendingVariant` を書くのは Owner の `SetVariant` / `ReqVariant` だけ (二重書きなし)。**Owner 自身は `SetVariant` の中で `ApplyVariant()` を呼ぶ** (`OnDeserialization` は Owner では走らない)。メニューは「次」を `PendingVariant >= 0 ? PendingVariant : Variant` から計算し、予約中は `試作: 横 → 遠く` と表示、押した時に犬が忙しければ「帰ってから切替」と出す (Codex X)。
- `ApplyVariant()` がプリセットを private 作業値へ展開する (`Start` と `OnDeserialization` で)。数値は public const (Verify が参照)。Inspector には出さない (評価ループは Build & Test なので、正本はコード)。
- 横曲がりは `catcher.FlightCurve` (variant から導く) を **投球の瞬間に `_Launch` が捕まえ**、ディスクは投球ごとの事実 `_curve` (p0 / v0 / 世代と同列) として飛行中ずっと使い、`ReqCatch` の第 6 引数 `curve` で犬 Owner へ渡して犬も同じ値を保持する。飛行中に番号を変えても進行中の飛行と予測は変わらない。ディスク側に独立した「設定値」は持たない (投球ごとの事実だけ) (Codex X)。
- **不変条件**: variant が触るのは Ready の目標・候補の選び方・踏み切り速度・着地の出口速度・クリップ選択・飛行の曲がりだけ。`GiveUp` / 地上回収 / `CanPlay` / `Claimed` (リード・集合が勝つ) / 空中で譲る予約 / playArea (`DogMayGo`) / 逸脱監視 は variant を見ない。

### 走り込み (v1〜3)

「外から走り込んでパッと取る」= 投球線の外に居た犬が、取れる区間 (7.5 m/s・10° なら投げ手から 9〜12 m、t ≥ 1.35 s) へ全力 (4.5 m/s) で走り込み、減速せずに取る。原型は **走り抜け** (PlanRun、既存) と **低い速い跳び** (rise 0.19〜0.40、踏み切り 4.0 m/s = 短いホップ)。高いジャンプ (rise 0.5〜0.75) は「止まって跳ぶ」印象になるので走り込みでは後回し。

Ready の幾何: 持ち主 `H`、頭の向き (水平) `f`、`r = Cross(up, f)`、`spot = H + f·ahead + r·lateral·side`。

| v | ahead | lateral | 待つ向き | 狙う進入角 (0 = 後ろから追う、90 = 横切る、180 = 正面) | 期待する見え方 |
|---|---|---|---|---|---|
| 0 | 8 (= standoffDistance) | 0 | 持ち主 | 正面〜追い | 現状。**式が現状と完全に同じ**であること |
| 1 | 7 | 4 | 持ち主 | 横切る (幾何上は 39〜63°、未検証の目標) | (4,7) から取れる区間へ 4.5〜6.4 m → 1.0〜1.4 s + 気づき 0.25 で t 1.4〜1.9 に間に合う |
| 2 | 11 | 1.5 | 持ち主 | 正面寄り (幾何上は 56〜143°、未検証の目標) | 閉じる速さが速いほど ±0.08 s 窓が厳しい (現状の正面と同じ性質) |
| 3 | 4 | 2.5 | 頭の向き `f` | 0〜30° | **7.5 m/s の平投げは追いつけず地上回収 = 仕様**。評価は 5〜6 m/s (スティック下) か仰角 20° 以上で |

- `side` は Ready に入った瞬間に `Dot(dog − H, r)` の符号で決めて Ready 中はラッチ (0 なら +1)。今居る側に置いて無駄走りと左右反転を防ぐ。
- 進入角の列は保証ではなく狙い。実際の進入角はログ `entry=` で分類し、「横切る勢い」「向かって来る迫力」「後ろから追いつく爽快さ」のどれが成立した投球かを分けて評価する (Codex X)。
- 首振りで待機場所が動かないように、**v1〜3 は Ready 入りの頭の向きをラッチ**し、向きが 45° (`RunInReadyTurnDeg`) 以上変わるか持ち主が 2.5 m (`RunInReadySlack`) 以上動いたときだけ目標を取り直す (犬を見るために 30° 振っても動かない。Codex U/X)。v0 は現状の距離ヒステリシス 1.5 m のまま (比較基準を変えない)。10 Hz 更新は現状どおり。playArea の丸め (円へ引き寄せ) も現状どおり → v2 の 11 m は**投げ手が広場の中央付近に立って**ようやく入る。
- 照準線は持ち主のクライアントにしか無い。犬 Owner が知れるのは頭の TrackingData なので Ready は頭の向きで置く (現状どおり)。走り込みの本体は投球後の計画で決まるので Ready の精度は「どこから走り出すか」にしか効かない。
- 計画器 (v1〜3 のときだけ): `RunInTakeoff 4.0` (踏み切り上限、`takeoffSpeed 2.5` の代わり) / `RunInPreferMaxRise 0.40` / `RunInJitSlack 0.30` / `RunInReadySlack 2.5`。`Plan` を 2 パスに: pass 0 (厳格) は `rise ≤ 0.40` (または走り抜け) かつ `avail − Eta ≤ 0.30 s` (= 全力で走ってちょうど間に合う候補) だけ、無ければ pass 1 = 現状どおり (必ず取りに行く)。着地後の減速は 0 ではなく `runSpeed 2.4` へ (走り抜けて向き直り、そのまま持ち帰る)。`Dot ≥ 0.3` の接近条件と空中速度上限 (chaseRunSpeed × 1.2) は変えない。
- 幾何の確認 (takeoff 4.0): rise 0.40 で tUp 0.286 s、クリップ倍率 1.22、実ため 0.20 s (0.82 m 前進)、空中水平 2.3 m、着地までの走行 ≈ 3.1 m。rise 0.19 で倍率 1.78 (上限 1.8 ぎりぎり)。キャッチ点が縁から 3 m 以内だと着地点が `DogMayGo` で落ちて地上回収 (保険どおり)。
- **クリップは v1〜3 では触らない**: 評価対象は「どこから・どれだけ速く来るか」で計画器だけで決まる。姿勢を同時に変えると比較が汚れる。4.0 m/s では着地〜回復の 0.25 s ほど足が滑って見える可能性があり、NG なら「走り取り」(ため無し・頭を下げる) クリップを次の候補にする。

### 取り方: ひねり (v4) とクリップ生成器の複数クリップ化

- `KH_FrisbeeJumpClipEditor` を「クリップ変種レコード」(名前・鍵の表・ため/上昇/回復の長さ・Animator の Bool 名) の配列にし、`Build` は全レコード、`Render` は変種ごとにシート。`KH_Jump_Lab.anim` の名前・内容は変えない。新規は `KH_Twist_Lab.anim` / `Data/Frisbee/KH_Twist_Lab.json`。`Key` に `twist` (up 軸のねじり) を足す。
- ひねりの鍵: Jump と同じ 10 キーを土台に、rise〜catch で twist 0 → 90°、bite で 90°、descend で 45°、touchdown で 0 (着地で進行方向へ戻る)。口位置の事実は facts が捕まえる。側面・斜めの図で脚の貫通・尾で立つ姿勢が無いことを確認して evidence へ。
- Catch は第 2 の facts セット (`*Twist`) を持ち、`ApplyVariant` が作業値へ写す。`ApplyState` は `Jump` / `Twist` の Bool を variant で分ける (全クライアントが同期済み値から導く)。`minRootRise` の下限 (高さ) は `g/2 × (clipRise/1.8)²` を両クリップの `clipRise` (上昇時間) で計算した大きい方 (Codex P: 高さと時間を混同しない)。

### 飛び方: 横曲がり (v5)

- `_PositionAt(p0, v0, curve, t)`: `side = Cross(up, v0flat).normalized`、横加速度 = `curve · vh2 · e^(−2kt)` (揚力と同じ「水平速度² に比例」)。**横速度にも他の水平速度と同じ抵抗 k がかかる** (`v_s' = curve·vh2·e^(−2kt) − k·v_s`) ので、横速度 = `curve · vh2 · (e^(−kt) − e^(−2kt)) / k`、横変位 = `curve · vh2 / k · ((1−e^(−kt))/k − (1−e^(−2kt))/(2k))`。初案の「揚力項と同じ積分」は横速度を減衰させておらず、Verify の積分照合で 0.6 m ずれて判明 → 抵抗ありに修正 (誤差 2.5 mm)。`CurveDefault = 0.04` (右曲がり。符号で左右。7.5 m/s・10° で着地 12 m のとき横へ約 1.9 m。設計初案の 0.15 は揚力項と同じ積分なので横 7 m も流れ、実装時に閉形式の再計算で判明して 0.04 へ変更)。
- 照準線・飛行・犬の予測の呼び出し (9 箇所) を同時に変える。Verify の閉形式 vs 積分に横加速度を足し、curve = 0 / ±CurveDefault (0.04) の 3 通り × 投球 3 種で最大誤差 < 1 cm。
- 「持ち主が選ぶ / 自動で変わる」はここでは決めない。

### 切替ボタン (手元メニューのヘッダ)

- ナイトモード型。`KH_HandMenu.devCatcher / devImage / devLabel`、`_DevVariant()` = 次の番号を `_RequestVariant`。ラベル `試作: {名前}`、色は 0 = 中立 / ≠0 = ON。表示は同期値を読むので他人が切り替えても全員のメニューが追従する。名前の文字列は `KH_HandMenu.cs` のリテラルに置く (字形が焼かれるのはこのファイルのリテラルだけ)。
- ヘッダの空き x −210〜165 に (−22, 312) 幅 350・18 pt で置く (予約中の最長ラベル `試作: 走り込み: 遠く → 走り込み: 並走` が 311 px で収まる。初案の幅 280・20 pt では 345 px で溢れた)。Verify のボタン数 47 → 48 + 2 項目。試作シーンにはメニューが無いので Interact キューブ (`KH_FrisbeeLauncher.cycleVariant`) を任意で足す。
- 撤去 / 本設定化は評価後に決める。撤去コミットでは Build Menu の古い子 (`Dev`) の掃除を 1 度入れる。

### 通常版の再現条件 (比較基準)

広場の中央付近に立つ / 強さは既定 (0.5 = 7.5 m/s) / 仰角 10° 前後 / 犬は Ready (8 m 前) / v=0。`throw v=0` のログを 3 回ぶん記録して基準にする。

## 評価の終点と判断点 (Codex P)

- 初回の評価対象は 6 プリセット (v0〜5) だけ。フリップ・風・ドッグキャッチは評価後に「試す / 見送る」を決め、見送りに実装は要らない。採用候補同士の組合せは別ラウンド (番号を足す) で、全組合せの制作は約束しない。
- **走り込みの評価を遅らせない判断点**: Wave 1 のゲート (Verify 失敗 0) を通った時点で走り込み 3 候補は単独で評価できる。Wave 2〜3 (ひねり・横曲がり) が難航して Wave 1 完了から実作業 1 日を超えるなら、先に走り込みだけで Build & Test を引き継ぐ。
- 「通常版の比較基準」は v0 の既存値・挙動 (slack 1.5、takeoff 2.5、着地で停止) を一切変えないことで保つ。

## PCVR 1 回目 (2026-09-21、ユーザー) と方針転換

**方針転換 (先回り型キャッチ)**: 「走りながら踏み切るタイミング勝負」をやめ、全プリセット共通で次の計画器にする。
- 投球直後 (気づき 0.1 s) に軌道を走査し、**取れる最初の (= 最も高い) 点**を選ぶ: rise ≤ maxRootRise (0.9 へ引き上げ)、`Eta + 落ち着き 0.25 s + ため + 上昇 ≤ 残り時間`、広場内、レーン・地面あり。rise が下限未満で立ち姿勢の口に届くなら「立って取る」(跳ばない)。
